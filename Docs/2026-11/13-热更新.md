## 一、热更新的基本概念

**热更新（Hot Update）**：游戏客户端不需要重新下载安装整个游戏，就可以通过网络下载新内容，并在适当时机加载和使用。

热更新主要分为两类：

| 类型       | 更新内容                          | 常用技术                  | 典型场景                   |
| ---------- | --------------------------------- | ------------------------- | -------------------------- |
| 资源热更新 | 模型、贴图、音效、地图、Prefab 等 | AssetBundle、Addressables | 新增皮肤、地图、特效       |
| 代码热更新 | 技能逻辑、玩法规则、功能实现      | Lua、HybridCLR            | 新增技能行为、修改程序逻辑 |

**核心区别：**

- 资源热更新解决的是“游戏使用什么内容”。
- 代码热更新解决的是“游戏如何执行逻辑”。

注意：如果原有程序已经支持某种行为，只需要修改配置参数，那么可能通过配置热更新实现，不一定需要更新代码。

## 二、AssetBundle（AB 包）

### 1. 基本概念

AssetBundle 是 Unity 提供的资源打包和运行时加载机制，可以将模型、贴图、音效、Prefab、场景等资源构建成独立的资源包。

它的核心作用是：**将游戏资源与客户端程序分开交付，实现按需下载、动态加载和独立更新。**

例如，游戏有三张地图：

```text
传统方式：
完整安装包
├── 游戏程序
├── 森林地图
├── 沙漠地图
└── 雪山地图

AB 包方式：
初始客户端
├── 游戏程序
└── 新手地图

远程资源服务器 / CDN
├── forest.bundle
├── desert.bundle
└── snow.bundle
```

玩家进入对应地图时，再下载和加载相应的资源包。

### 2. AB 包的优点

- **减少初始安装包体积**：不必提前下载全部游戏资源。
- **支持按需加载**：进入特定场景时再获取相应资源。
- **支持资源独立更新**：更新皮肤、地图等内容，无需重新发布完整客户端。
- **减少重复下载**：未发生变化的资源包可以继续使用本地版本。

需要注意，AB 包本身只是资源容器，不包含完整的版本检查、网络下载、更新回滚等机制，也不能直接执行新的 C# 代码。

## 三、资源热更新的实现流程

资源热更新通常需要客户端、更新服务器、资源清单和本地缓存共同完成。

### 1. 基本流程

```text
游戏客户端启动
      ↓
请求服务器上的资源更新清单
      ↓
与本地资源清单进行比较
      ↓
确定新增或发生变化的资源包
      ↓
下载需要更新的 AB 包
      ↓
校验资源完整性
      ↓
更新本地资源清单并切换版本
      ↓
动态加载新资源
      ↓
进入游戏
```

### 2. 资源清单（Manifest）

资源清单用于记录资源包的版本、Hash、文件大小及依赖关系等信息。

示例：

```json
{
  "version": "1.1.0",
  "bundles": [
    {
      "name": "forest.bundle",
      "hash": "abc123",
      "size": 104857600
    },
    {
      "name": "skin.bundle",
      "hash": "def456",
      "size": 10485760
    }
  ]
}
```

客户端通过比较本地和服务器的资源清单，判断需要更新哪些资源。

| 资源包        | 本地 Hash | 服务器 Hash | 处理方式         |
| ------------- | --------- | ----------- | ---------------- |
| forest.bundle | abc123    | abc123      | 继续使用本地资源 |
| skin.bundle   | def123    | def456      | 下载新资源       |
| sound.bundle  | ghi789    | ghi789      | 继续使用本地资源 |

**核心思想：只下载新增或发生变化的资源包。**

实际项目还需要考虑下载失败重试、资源依赖、缓存清理、版本回滚和安全校验。

## 四、AB 包的分包策略

资源包的拆分方式直接影响更新体积、加载效率和资源占用。

### 1. 按更新频率拆分

假设一张地图为 500 MB，活动图标为 1 MB。

- **不合理分包**：地图和图标放在同一个 AB 包中，修改图标可能导致整个约 501 MB 的资源包重新下载。
- **合理分包**：地图和活动图标分别打包，只需要下载更新后的图标包。

### 2. 避免过度拆分

分包并不是越细越好。

如果每张图片都单独打包，可能导致：

- 资源包和文件数量过多。
- 下载请求和加载管理开销增大。
- 资源依赖关系复杂。
- 资源卸载和内存管理困难。

### 3. 处理公共资源依赖

如果多个角色使用相同的材质和贴图，应考虑将公共资源单独打包，避免在多个资源包中重复包含。

例如：

```text
shared.bundle
    ├── 公共材质
    └── 公共贴图
          ↑
    ┌─────┴─────┐
    │           │
heroA.bundle  heroB.bundle
```

加载角色资源时，需要正确处理公共资源包的依赖。

**分包原则：经常变化的资源尽量独立；经常一起使用和更新的资源可以合并；公共依赖资源尽量避免重复打包。**

## 五、代码热更新

资源热更新只能替换游戏资源，不能直接使客户端执行原本不存在的程序逻辑。

例如，原来的火球只能直线飞行，现在希望火球自动追踪敌人。如果原有代码没有追踪能力，就需要修改或增加程序逻辑。

代码热更新通常需要提前接入相应的运行时方案。

### 1. Lua 热更新

Lua 是一种脚本语言，可以通过 Lua 运行环境执行动态下载的游戏逻辑。

基本流程：

```text
Unity C# 客户端
      ↓
调用 Lua 运行环境
      ↓
加载 Lua 技能脚本
      ↓
执行技能逻辑

更新时：
服务器发布新版 Lua 脚本
      ↓
客户端下载
      ↓
重新加载新版脚本
      ↓
执行新逻辑
```

特点：

- 游戏逻辑可以通过脚本动态更新。
- 适合技能、任务、UI 等部分业务逻辑。
- 需要预先设计 C# 与 Lua 的交互接口。
- 需要额外维护 Lua 运行环境和脚本体系。

### 2. HybridCLR 热更新

HybridCLR 是面向 Unity IL2CPP 环境的 C# 热更新解决方案，可以支持动态加载和执行符合要求的托管程序集。

基本流程：

```text
编写 C# 热更新逻辑
      ↓
编译 HotUpdate.dll
      ↓
发布到资源服务器
      ↓
客户端下载 DLL
      ↓
HybridCLR 加载程序集
      ↓
执行新版 C# 逻辑
```

特点：

- 热更新逻辑可以继续使用 C# 编写。
- 与 Unity 原有 C# 技术体系较为一致。
- 需要提前集成 HybridCLR 运行环境。
- 需要处理程序集依赖、兼容性及平台限制。

注意：代码热更新并不意味着可以任意修改所有底层功能。原生插件、引擎功能和部分平台相关功能仍可能需要发布新客户端。

## 六、AB、Addressables、Lua 和 HybridCLR 的关系

| 技术         | 技术定位               | 主要用途                           |
| ------------ | ---------------------- | ---------------------------------- |
| AssetBundle  | Unity 资源包及加载机制 | 资源打包、加载和独立分发           |
| Addressables | Unity 资源管理系统     | 资源寻址、依赖管理、加载和远程更新 |
| Lua          | 脚本语言及其运行环境   | 动态执行脚本逻辑                   |
| HybridCLR    | C# 热更新运行时方案    | 动态加载和执行 C# 程序集           |

它们之间的关系可以理解为：

```text
游戏热更新
│
├── 资源热更新
│   ├── AssetBundle
│   │   └── 资源打包与加载
│   │
│   └── Addressables
│       └── 资源寻址、依赖和更新管理
│           （底层可使用 AssetBundle）
│
└── 代码热更新
    ├── Lua
    │   └── 动态执行 Lua 脚本
    │
    └── HybridCLR
        └── 动态执行 C# 程序集
```

**Addressables 与 AssetBundle 并不是完全对立的技术。** Addressables 可以基于 AssetBundle 实现更高层次的资源管理。

## 七、多人游戏中的热更新

对于采用 **Unity 客户端 + C++ 权威服务器** 的多人游戏，还需要区分客户端更新与服务端更新。

例如新增一个自动追踪技能：

| 更新对象   | 更新内容                     | 可能采用的方式       |
| ---------- | ---------------------------- | -------------------- |
| 客户端资源 | 技能模型、特效、音效         | AB / Addressables    |
| 客户端逻辑 | 追踪效果、动画控制、表现逻辑 | C# / Lua / HybridCLR |
| 服务端逻辑 | 目标选择、命中判定、伤害计算 | 更新 C++ 服务端程序  |

由于采用权威服务器架构，客户端展示出的技能效果不代表服务器认可该行为。

服务器应负责验证或执行关键战斗逻辑，避免客户端通过修改代码伪造技能命中或伤害结果。

因此，多人游戏发布更新时，还应考虑：

- 客户端和服务端版本兼容。
- 网络协议字段及消息格式兼容。
- 新旧技能逻辑的同步。
- 服务器更新时的房间与玩家会话处理。

## 八、核心总结

| 核心问题                           | 解决方法                             |
| ---------------------------------- | ------------------------------------ |
| 为什么不用重新安装整个游戏？       | 将部分资源和逻辑独立交付，实现热更新 |
| 如何动态加载新地图和新皮肤？       | AssetBundle / Addressables           |
| 如何判断需要下载哪些资源？         | 比较本地与服务器的资源清单           |
| 为什么需要合理拆分 AB 包？         | 降低更新体积、减少资源重复及加载开销 |
| 如何动态修改原本不支持的技能逻辑？ | Lua / HybridCLR 等代码热更新方案     |
| AB 能直接执行新 C# 代码吗？        | 不能，必须依赖额外的执行机制         |
| 多人游戏的核心战斗逻辑由谁负责？   | 权威服务器负责验证或执行             |

### 推荐学习路线

1. **AssetBundle**：掌握资源打包、运行时加载、依赖关系及卸载。
2. **Addressables**：掌握资源寻址、异步加载、缓存和远程资源更新。
3. **资源版本管理**：实现 Manifest 对比、增量下载、Hash 校验及版本回滚。
4. **代码热更新**：了解 Lua、HybridCLR 的运行原理及适用场景。
5. **多人游戏版本管理**：理解客户端资源、客户端代码和权威服务器之间的版本兼容问题。

**一句话总结：热更新是目标，AB 包是资源载体，Addressables 是资源管理方案，Lua 和 HybridCLR 是代码动态执行方案；完整的游戏热更新系统还需要版本管理、网络下载、缓存、校验与回滚等机制。**
