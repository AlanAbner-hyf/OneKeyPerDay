##### 游戏编程模式

我认为几个比较重要的设计模式：

* 命令模式：命令模式实际上是一种回调的面向对象实现，而命令则是具现化的方法调用。在游戏开发中，命令一般代表一个可以触发的游戏行为，比如跳跃、攻击等。而且帧同步一般都伴随着命令模式，因为这样可以方便地模拟各个客户端，每次世界更新就是客户端处理一系列的命令。而且命令模式也很适合做AI，因为可以在AI和玩家控制的角色之间使用相同的命令模式，AI代码只需要生成Command对象即可。还有一个很重要的点就是命令模式可以很方便地做到撤销和重做，只需要用一个数据结构按照顺序存储各个命令即可，因为这个性质，一般可以拿来做回放系统。
* 享元模式：一般当需要共享类的时候可以使用享元模式。享元模式通过将对象的数据分为两种来解决这个问题。 第一种数据**没有特定指明是哪个对象的实例**，因此可以在它们间分享。数据的剩余部分是**变化状态**，那些每个实例独一无二的东西。实例渲染的时候会涉及到享元模式，因为每一个实例的模型和贴图其实都一样，只是它们的位置，旋转等数据不同，因此将模型和贴图作为享元非常合适，这样只需要把模型（网格）上传一次到GPU，然后用一个数组存储每个实例不同的变换矩阵（位置、旋转、缩放），通过**一次绘制调用**（Draw Call）让GPU批量画出所有实例。同时，享元模式往往和工厂模式相结合，因为享元的核心就是每种类型只共享一份对象，所有对象的创建需要被管控，不能随意new Object，而工厂模式恰好能够几种创建逻辑。
* 观察者模式：这里用一个成就系统举例。在游戏开发中，如果不小心，成就系统可能会缠绕在代码的很多角落。比如玩家击败了100只史莱姆，成为史莱姆克星，这就容易和战斗模块耦合，需要在击败史莱姆的时候进行计数，这不是我们希望看到的。而且这还只是一个成就，实际上游戏可能有各种各样的成就，所以如何解耦成就系统和其它部分呢？看一下观察者模式的一种简单实现。

```C++
// 观察者接口
class Observer
{
public:
  virtual ~Observer() {}
  virtual void onNotify(const Entity& entity, Event event) = 0;
};

// 实现--成就系统
class Achievements : public Observer
{
public:
  virtual void onNotify(const Entity& entity, Event event)
  {
    switch (event)
    {
    case EVENT_ENTITY_FELL:
      if (entity.isHero() && heroIsOnBridge_)
      {
        unlock(ACHIEVEMENT_FELL_OFF_BRIDGE);
      }
      break;

      // 处理其他事件，更新heroIsOnBridge_变量……
    }
  }

private:
  void unlock(Achievement achievement)
  {
    // 如果还没有解锁，那就解锁成就……
  }

  bool heroIsOnBridge_;
};

// 被观察者接口
class Subject
{
private:
  Observer* observers_[MAX_OBSERVERS];
  int numObservers_;
// 允许了外界代码控制谁接收通知
public:
  void addObserver(Observer* observer)
  {
    // 添加到数组中……
  }

  void removeObserver(Observer* observer)
  {
    // 从数组中移除……
  }
// 发送通知
protected:
  void notify(const Entity& entity, Event event)
  {
    for (int i = 0; i < numObservers_; i++)
    {
      observers_[i]->onNotify(entity, event);
    }
  }
  // 其他代码……
};
// 实现--物理系统
// 真实代码中，物理系统一般不会继承自Subject，而是有一个Subject实例
class Physics : public Subject
{
public:
  void updateEntity(Entity& entity);
};
```

这里要注意区分观察者模式和事件模式。观察者模式中观察的是做事的主体本身，比如物理系统；而事件系统观察的是代表事件本身的对象，比如下落事件。一般其实更倾向于事件系统，因为事件系统解耦得更彻底。

这里还有一个问题就是在真实的项目中，观察者列表随着观察者的添加和删除而动态地增长和缩短。所以需要一种无需任何动态分配的方式来增加和删除观察者，有链式观察者或者链表节点池等方案。

观察者模式真正的缺点是比较**难看懂代码。不容易定位漏洞**。

* 单例模式：*保证一个类只有一个实例，并且提供了访问该实例的全局访问点。* 单例模式很方便使用，但是更重要的是单例模式的缺点。首先就是单例模式会创建一个全局变量，而全局变量会导致理解代码更加困难，促进耦合发生，对并行也不友好。其次就是有时候是需要有多个实例的。最后就是单例的惰性初始化剥夺了控制权。
* 状态模式：说到状态模式就不可避免说的有限状态机。有限状态机一般有两种实现方式，一个是**使用枚举类型，另一个就是为每个状态创建一个类，有一个共同的状态基类**。可以在这个基类中添加进入状态，离开状态调用的函数。同时一个状态可以有多个对象也可以只有一个对象，当状态不涉及到某一个实体独有的属性时，不同的实体可以共用相同的状态对象。而且一个实体也不是只能有一个状态机，可以有多个状态机，比如对于角色来说，一个控制普通行为，一个控制武器行为。还有分层状态机，即一个状态可以继承自另一个状态。还有下推状态机，普通的有限状态机没有历史的概念，这样无法重回上一状态，因此下推状态机使用了一个栈来保存状态，栈顶是当前状态。
* 双缓冲模式：*用序列的操作模拟瞬间或者同时发生的事情*。

##### 强化学习

一种**通过与环境交互、根据奖励反馈学习决策**的机器学习方法。

关注的核心问题是：在连续做决策的时候怎么使得长期收益最大。

例子：机器人走迷宫，不告诉机器人如何走而是设置规则，达到终点得到奖励，撞墙受到惩罚，每走一步都需要一定的成本。机器人反复尝试，逐渐学会选择更容易到达终点、耗时更少的路线。

一些基本概念：

|  概念  | 含义                   | 迷宫示例                 |
| :----: | ---------------------- | ------------------------ |
| 智能体 | 做决策的主体           | 机器人                   |
|  环境  | 智能体位于的系统       | 迷宫                     |
|  状态  | 环境的当前状况         | 机器人位置，陷阱等       |
|  动作  | 智能体可采取的行为     | 上下左右移动             |
|  奖励  | 环境对行动给出的反馈   | 终点加分，撞墙、陷阱扣分 |
|  策略  | 根据环境的状态选择动作 | 往哪走                   |

学习过程：观察当前状态->选择动作->获得奖励并进入新状态->利用经验改进策略->继续尝试

强化学习与其它常见的机器学习方法的区别可以从**学习信号来自哪里**进行理解：

| 学习方式   | 主要学习信号             | 例子                     |
| ---------- | ------------------------ | ------------------------ |
| 监督学习   | 已知的正确答案或标签     | 用标注图片学习识别狗     |
| 无监督学习 | 数据本身的结构           | 将相似信息分组           |
| 强化学习   | 行动产生的奖励与后续结果 | 学习游戏操作或机器人控制 |
