# 二、网易 Joker：Shader 与图形方向

## Q2：你说把 Unity Shader 移植到 NeoX3，主要难点是什么？

### 推荐回答

最大的问题其实不是 HLSL 语法，而是两个引擎对 Shader 数据和渲染约定不同。

我当时主要遇到三类问题。

第一类是坐标系差异，例如 UV 的 Y 轴方向不同。如果直接照搬 Unity Shader，结果就可能上下翻转。

第二类是 Shader API 和函数语义差异。例如 Unity 中一些 Repeat 效果直接依赖 `frac()` 或材质系统提供的 Wrap Mode，但自研引擎里行为不完全一致，所以需要自己模拟。

第三类是颜色空间和 HDR 表达差异。即使数学计算完全相同，不同引擎在颜色输入、HDR 强度、采样结果处理上的约定不同，也会造成最终视觉差异。

所以我的迁移流程不是单纯改代码，而是先把 Unity 的效果拆成输入、UV 变换、采样、颜色计算几个阶段，然后逐层在 NeoX3 对齐。

---

## Q3：什么是 Domain Warp？

### 推荐回答

Domain Warp 本质上是“用一个噪声去扰动另一个采样的坐标”。

普通噪声可能是：

```cpp
color = Noise(UV);
```

Domain Warp 则类似：

```cpp
offset = Noise1(UV);
color = Noise2(UV + offset);
```

这样最终看到的就不是规则噪声，而是被扭曲过的流动结构。

我当时剑气效果里用双层噪声扰动 UV，然后再配合 Flowmap 做方向性运动，这样比简单滚动贴图更自然。

### 追问：为什么不直接滚 UV？

单纯：

```cpp
UV += time * speed;
```

会产生明显的整体平移感，尤其重复纹理容易看出来周期。

Domain Warp 可以破坏这种规则性，使局部区域运动速度和方向发生变化，所以更接近烟雾、能量或者剑气这种非刚性效果。

---

## Q4：Flowmap 是什么？

### 推荐回答

Flowmap 本质上是一张存储二维流动方向的纹理。

一般可以用 RG 两个通道分别表示 XY 方向。

Shader 中读取：

```cpp
flow = texture(flowMap, uv).rg;
```

再把 `[0,1]` 映射到 `[-1,1]`：

```cpp
flow = flow * 2 - 1;
```

然后用它扰动纹理采样位置。

这样不同位置的纹理就可以沿不同方向移动，而不是所有像素统一滚动。

---

## Q5：为什么 Flowmap 要错相双采样？

### 推荐回答

Flowmap 如果一直按照：

```cpp
UV + flow * time
```

去移动，随着 time 增大，采样位置会持续偏移，纹理会出现拉伸或者周期跳变。

解决办法是准备两个时间相位，例如：

```cpp
phase1 = frac(time);
phase2 = frac(time + 0.5);
```

分别采样两次，然后根据 phase 做 Cross Fade。

当第一组 UV 即将发生重置时，第二组刚好处于稳定区域。

最后把两组结果混合，就可以隐藏 UV 重置带来的跳变。

# 三、倒水效果：Batch / Stencil / Mask

## Q6：为什么 Stencil 会导致断 Batch？

### 推荐回答

Batch 的前提是多个 Draw Call 的渲染状态足够一致。

{

	为什么Batch 的前提是多个 Draw Call 的渲染状态足够一致？

	Batch 本质上是把多个原本独立提交的几何对象合并到一次 Draw Call 中。一次 Draw Call 执行期间 GPU 使用的是一套确定的 Pipeline State，比如 Shader、Texture、Blend、Depth、Stencil 等。如果两个对象需要不同的 Pipeline State，就必须先结束当前绘制、切换状态，再提交新的 Draw Call，因此无法直接合批。

	但对象的位置、UV、颜色这些差异不一定影响 Batch，因为可以把它们作为 Vertex Data 或 Instance Data 传给同一个 Shader。所以判断能不能合批的核心，不是“两个物体完全一样”，而是**它们能不能由同一套渲染管线处理，只把差异作为数据输入进去。**

}

Stencil Test 本身属于 GPU Pipeline State 的一部分。

使用 ClippingNode 时通常需要：

1. 先写 Stencil Buffer
2. 修改 Stencil Compare
3. 再绘制被裁剪对象

中间发生了渲染状态切换，所以无法和前后的普通 Sprite 继续合批。

最终会产生额外 Draw Call。

我后来把裁剪改成 Shader 中采样 Mask Texture 的 alpha，例如：

```cpp
if(maskAlpha < threshold)
    discard;
```

或者直接乘到最终 alpha 上。

这样就不需要频繁修改 Stencil State，因此可以保持更多对象处于同一个 Batch。

---

## Q7：那为什么所有东西都不用 Stencil，直接 Mask？

### 推荐回答

Mask Texture 的代价是额外纹理采样。

Stencil 的优势是 GPU 有专门的 Stencil Test，而且复杂遮罩情况下可能比 Shader 采样更划算。

所以不是 Mask 一定优于 Stencil。

我这个场景的问题是 UI / Sprite 数量多，而且 Batch 数量是主要瓶颈，因此减少 Pipeline State 切换带来的收益大于一次 Mask 采样的成本。

# 四、2D Sprite 破坏：核心项目

## Q8：你的 Sprite 破坏系统具体是怎么实现的？

### 推荐回答

这个需求本质上是弹弹堂类似的可破坏 2D 地形。

一开始的实现是基于整张 Bitmap。

每次爆炸之后修改 alpha，然后重新对整张图执行 Marching Squares，提取轮廓，再重新生成 Mesh。

问题是随着图片越来越大，每次爆炸都需要处理大量没有变化的像素，CPU 开销比较高。

所以第一阶段我做了局部化优化：

爆炸之后计算 Dirty Rect，只处理受影响区域。

然后通过扫描线连通域找到受到影响的岛屿，只对对应子区域重新执行 Marching Squares 和 Mesh 重建。

在这个基础上又进一步做了分区复用，减少重复计算。

之后我又实现了一条纯多边形方案。

把原地形轮廓维护为 Polygon，然后将爆炸圆近似为多边形，对两者做 Boolean Difference。

因为引擎里没有现成 Polygon Boolean，我自己实现了 Weiler-Atherton 的弧段编织算法。

最后又解决了浮点退化、边界重合等问题。

最终把一次爆炸的计算时间从几十毫秒降低到了毫秒级。

### 推荐叙事结构

- 原始方案
- 性能问题
- 第一阶段优化
- 第二阶段优化
- 最终结果

---

## Q9：Marching Squares 是什么？

### 推荐回答

Marching Squares 是 Marching Cubes 在二维情况下的版本，作用是从二值图中提取等值线。

对一个 `2×2 Cell` 的四个角进行 inside / outside 判断。

每个角只有 0 和 1 两种状态，所以一共有：

```text
2^4 = 16
```

种情况。

根据 Lookup Table 判断轮廓线穿过哪些边。

例如：

```text
1 ---- 0
|      |
|      |
1 ---- 0
```

左边 inside，右边 outside，那么轮廓大概率穿过上下两条边的中点。

对整个 Bitmap 遍历之后，就可以得到大量线段，再把线段连接成 LoopChain。

---

## Q10：Marching Squares 有没有 Ambiguous Case？

### 推荐回答

有。

例如：

```text
1 0
0 1
```

或者：

```text
0 1
1 0
```

对角 inside 时会出现歧义，因为可能有两种连接方式。

一般可以通过中心点采样或者 Asymptotic Decider 等方法判断拓扑。

在游戏场景中也可以根据已有轮廓连续性做规则化处理。

---

## Q11：Dirty Rect 为什么能显著优化？

### 推荐回答

因为爆炸实际上只影响一个很小区域。

如果 Sprite 是 `2048×2048`，重新扫描整张图需要处理 400 多万个像素。

而如果爆炸范围只有 `100×100`，那么理论上只需要处理约 1 万个像素。

所以复杂度从与整个图片面积相关：

```text
O(W × H)
```

变成与局部破坏面积相关：

```text
O(w × h)
```

游戏里的绝大多数爆炸都是局部修改，因此收益非常明显。

---

## Q12：既然 Bitmap + Dirty Rect 已经优化了，为什么还要做 Polygon？

### 推荐回答

Dirty Rect 解决的是“少扫描像素”，但是 Bitmap 方案的本质仍然是：

```text
Pixel → Contour → Mesh
```

每次都存在轮廓重建过程。

Polygon 方案则直接维护几何表示。

爆炸变成：

```text
TerrainPolygon - ExplosionPolygon
```

得到的新 Polygon 可以直接用于 Mesh。

当破坏次数比较多时，可以减少 Bitmap 到 Polygon 的反复转换。

代价是 Polygon Boolean 的实现复杂度明显更高，而且浮点鲁棒性问题比较严重。

---

## Q13：Weiler-Atherton 是干什么的？

### 推荐回答

它是一种 Polygon Clipping / Boolean 算法。

核心思想是：

1. 计算两个 Polygon 的所有交点
2. 把交点插入双方的顶点链
3. 判断每个交点是进入还是离开
4. 从某个交点出发，在两个 Polygon 的边界之间切换遍历
5. 拼接出最终的交集、差集或者其他结果

我的场景是：

```text
Terrain - Explosion
```

所以主要实现的是 Difference。

---

## Q14：什么情况下会出现浮点退化？

### 推荐回答

比如：

- 一个爆炸 Polygon 的顶点刚好落在地形 Polygon 的边上
- 两条边几乎平行
- 交点和已有顶点非常接近
- 多个交点距离小于 epsilon

理论上应该重合的坐标，在浮点计算里可能变成：

```text
0.99999997
```

和：

```text
1.00000002
```

导致算法判断成两个不同点。

最终可能出现零面积 Polygon、自交或者错误拓扑。

所以实际工程里需要：

- epsilon 判断
- 点合并
- 去零面积边
- 特殊边界情况处理

我当时还加入了非常小的亚像素 jitter 作为极端退化情况下的兜底。

---

## Q15：你是怎么把 69ms 优化到毫秒级的？

### 推荐回答

我主要做了三件事。

第一，缩小计算范围：整图处理变成 Dirty Rect。

第二，缩小重建对象：利用连通域找到受影响的 Island，而不是所有 Mesh 都重建。

第三，改变数据表示：部分场景从 Bitmap → Polygon → Mesh，变成直接 Polygon Boolean。

所以本质是：

> 减少数据量 + 减少无效计算 + 避免重复转换。

我认为这比单纯做微观代码优化收益更大。

### 可强调的工程思想

性能优化优先顺序通常应该是：

1. 先减少工作量
2. 再优化算法复杂度
3. 最后做局部代码级微优化

# 五、音频频谱可视化

## Q16：为什么 10Hz 数据可以显示 60fps？

### 推荐回答

因为数据采样频率和视觉刷新频率没有必要相同。

频谱真正的新数据每 100ms 来一次：

```text
10Hz
```

但是画面可以每：

```text
16.67ms
```

更新一次。

假设当前数据是 A，下一帧数据是 B。

在 A 到 B 之间做插值：

```cpp
value = lerp(A, B, t);
```

就可以产生中间视觉状态。

所以视觉可以是 60fps，而底层数据仍然只有 10Hz。

---

## Q17：为什么不直接把数据重采样成 60Hz？

### 推荐回答

没必要。

如果直接把数据离线或者实时扩成 60Hz，相当于数据量变成 6 倍。

但这些新增数据本质上都是插值得到的。

所以更合理的是：

1. 保留原始 10Hz 数据
2. Renderer 根据当前时间在相邻数据帧之间动态插值

这样可以减少内存和数据处理开销。

同时如果视觉某一帧掉帧，也不会破坏数据时间轴。

---

## Q18：为什么这个方案还能做“掉帧保护”？

### 推荐回答

因为动画状态不是依赖：

```text
上一帧状态 + Delta
```

一直累积计算，

而是根据：

```text
当前时间 → 数据帧索引 → 插值
```

直接求状态。

比如某一帧从 16ms 掉到 50ms，下一帧仍然按照真实播放时间计算对应的数据位置。

所以只会少显示几个中间视觉帧，不会导致整体音画时间轴越来越偏。

# 六、Tracy 与性能分析

## Q19：你为什么用 Tracy？怎么看性能问题？

### 推荐回答

我一般不会一看到卡顿就直接改代码，而是先 Profiling。

我的流程通常是：

1. 先确认问题属于 CPU、GPU、IO 还是内存
2. CPU 再看 Frame Timeline
3. 找异常 Spike
4. 继续向下找到具体函数
5. 判断它是算法复杂度问题、调用次数问题，还是同步阻塞

Tracy 的优势是时间线非常直观，可以看到每帧各个 Zone 的耗时以及线程关系。

我在频谱项目里用它主要是确认插值和数据 / 视觉解耦没有产生新的明显 CPU 开销。

# 七、腾讯天美：Chaos 物理系统

## Q21：为什么需要连接 Dedicated Server？

### 推荐回答

在多人游戏里，很多关键物理逻辑实际运行在服务器。

如果只看客户端状态，有可能看到的是复制或者插值后的结果，而不是权威物理状态。

Dedicated Server 是 Authoritative Side，所以直接调试 Server Physics State 更容易定位真正的问题。

比如：

客户端看到角色突然弹飞，

原因可能不是客户端插值，而是服务器某一帧发生了错误碰撞。

这时应该看 Server 上的 Chaos 状态。

# 八、HeapSnapshot 与内存分析

## Q22：Heap Snapshot 是什么？

### 推荐回答

Heap Snapshot 本质上是某一时刻堆内存对象关系的快照。

它不仅记录对象占用了多少内存，还记录对象之间的引用关系。

所以它比单纯看 Allocation 大小更有价值。

内存泄漏很多时候不是对象特别大，而是某个引用没有释放，导致一整个对象图都无法回收。

---

## Q23：Shallow Size 和 Retained Size 有什么区别？

### 推荐回答

Shallow Size 是对象本身占用的内存。

Retained Size 是：

如果这个对象被释放，因为它而间接可以释放的所有对象总大小。

例如：

```text
A
|
B
|
C
```

A 自己可能只有 100B。

但是如果 B、C 都只能通过 A 被引用，那么 A 的 Retained Size 可能是：

```text
A + B + C
```

所以定位内存泄漏时，Retained Size 往往比 Shallow Size 更有意义。

---

## Q24：什么叫内存泄漏？

### 推荐回答

广义上内存泄漏是：

> 已经不再被业务需要的对象仍然保持可达状态，导致内存不能释放。

C++ 里可能是：

```cpp
new
```

后没有：

```cpp
delete
```

也可能是 `shared_ptr` 循环引用。

GC 语言里虽然一般不会忘记 free，但是如果某个全局容器一直持有对象引用，同样会造成逻辑意义上的泄漏。

# 九、AI 卡牌项目

## Q25：为什么行为树、遗传算法和强化学习都用了？

### 推荐回答

三者其实解决的问题不同。

行为树主要解决的是可解释的规则决策。

比如：

- 血量低于多少回血
- 什么情况下防御
- 什么情况下攻击

这种规则非常适合行为树。

遗传算法解决的是参数和策略组合搜索问题。

我可以定义一个适应度函数，然后让不同策略之间进行选择、交叉和变异。

强化学习则希望探索规则之外的策略，让 Agent 通过对战结果学习长期收益。

所以我的思路不是用三种算法同时控制一个 NPC，而是拿它们对比：

> 规则式 AI、搜索式 AI、学习式 AI

在同一个卡牌战斗环境里的效果和开发成本。

---

## Q26：为什么不是全部用强化学习？

### 推荐回答

因为强化学习最大的缺点是训练成本和可控性。

游戏里的 NPC 往往不是越强越好。

还要满足：

- 可解释
- 难度可控
- 策划可以调整
- 行为稳定

行为树在这方面反而非常好。

所以工业游戏 AI 通常不会简单地认为 RL 可以完全替代规则 AI。

---

## Q27：遗传算法怎么用到卡牌游戏？

### 推荐回答

我把一个策略看成一个个体。

比如策略参数包括：

- 攻击倾向
- 防御倾向
- 保留高费卡倾向
- 血量阈值
- 技能释放权重

然后让不同个体进行大量对战。

根据胜率、剩余血量、伤害等设计 Fitness。

Fitness 高的个体更容易被保留。

再进行：

- Selection
- Crossover
- Mutation

多代迭代后找到表现更好的参数组合。

### 追问：Fitness 怎么设计？

如果只用胜负，反馈非常稀疏。

可以做加权：

```text
Fitness =
WinReward
+ HPReward
+ DamageReward
- TurnPenalty
```

但权重需要控制，否则可能出现 Agent 为刷伤害而不追求胜利的情况。

---

## Q28：强化学习中的 Reward 怎么设计？

### 推荐回答

最核心奖励一定还是：

- Win：正奖励
- Lose：负奖励

但如果只有最终奖励，会存在 Reward Sparse。

所以训练早期可以加入一些辅助奖励：

- 对敌人造成有效伤害
- 合理使用卡牌
- 保持自身血量

但 Reward Shaping 不能太强。

否则模型可能学会“刷奖励”，却不真正追求胜利。

# 十、坦克大战：网络方向

## Q29：为什么 TCP 会粘包？

### 推荐回答

因为 TCP 是字节流协议。

TCP 不保留应用层消息边界。

假设调用两次 Send：

```text
Send(A)
Send(B)
```

接收端可能：

```text
Recv(A+B)
```

也可能：

```text
Recv(A的一部分)
Recv(剩下的A+B)
```

所以所谓粘包、拆包本质上不是 TCP 出错，而是应用层必须自己定义消息边界。

### 一句话总结

> TCP 没有应用层“消息包”的概念，只有连续字节流。

---

## Q30：如何解决 TCP 粘包？

### 推荐回答

我采用 Length-Prefix。

数据结构类似：

```text
| Length | Message |
```

接收 Buffer 后：

1. 先判断是否至少有 Header
2. 读取 Length
3. 判断 Buffer 是否至少有 Length 个字节
4. 如果够，就解析一个完整 Message
5. 不够就继续等待
6. 循环处理 Buffer 中可能存在的下一条消息

---

## Q31：为什么游戏一般使用 UDP？

### 推荐回答

最关键的原因其实不是“UDP 比 TCP 快”。

而是 UDP 允许应用层自己决定：

> 哪些数据值得重传，哪些数据过期就应该直接丢弃。

游戏状态具有非常强的实时性。

比如：

```text
Player Position t=1
Player Position t=2
```

如果 t=1 丢了，但是 t=2 已经到了，其实没有必要再重传 t=1。

TCP 为了保证 Reliable + Ordered，必须等待 t=1。

这会导致 Head-of-Line Blocking。

所以实时游戏往往使用 UDP，再在上层针对关键数据实现可靠机制。

---

## Q32：那为什么你的坦克大战用 TCP？

### 推荐回答

因为这个项目主要目的是学习 C/S 网络架构，而不是实现高频 FPS 网络同步。

坦克大战的数据规模和同步频率也比较有限，所以 TCP 已经可以满足需求，而且实现复杂度更低。

如果让我重新做一个实时竞技项目，我会倾向：

- 登录、商城、聊天等低频可靠数据：TCP / HTTP
- 战斗状态同步：UDP + 应用层可靠机制

---

## Q33：什么是大小端？

### 推荐回答

假设：

```text
0x12345678
```

内存地址从低到高。

Big Endian：

```text
12 34 56 78
```

Little Endian：

```text
78 56 34 12
```

网络协议通常使用 Network Byte Order，也就是 Big Endian。

所以跨平台传输整数时需要做字节序转换。

---

## Q34：为什么消息路由要用反射？

### 推荐回答

如果不用反射，很容易写成：

```cpp
switch(msgId)
{
case Login:
    HandleLogin();
case Move:
    HandleMove();
...
}
```

消息越来越多之后这个中心 Dispatch 会非常臃肿。

使用反射之后，可以约定：

```text
MsgLogin -> OnMsgLogin
MsgMove  -> OnMsgMove
```

收到消息之后根据消息类型查找 Handler。

这样新增消息时不需要不断修改巨大 switch，可以降低消息模块之间的耦合。

---

## Q35：反射有什么缺点？

### 推荐回答

最大的问题是把一部分编译期检查变成了运行期检查。

如果函数名写错，编译可能不会报错，而是在运行时找不到 Handler。

另外反射本身也有一定性能开销。

所以更成熟的方案可以在启动阶段缓存：

```text
MessageID → Function
```

避免每条消息都动态做反射查找。

---

## Q36：TCP 已经能检测断线，为什么还需要 Heartbeat？

### 推荐回答

TCP 能检测连接异常，但不一定能及时检测。

比如客户端突然断电或者网络物理中断，连接可能会在一段时间内仍然保持 ESTABLISHED。

游戏服务器不能一直保留这些资源。

所以客户端周期发送 Heartbeat。

Server 保存：

```text
LastHeartbeatTime
```

如果：

```text
Now - LastHeartbeatTime > Timeout
```

就认为客户端失联并释放资源。

# 十一、C++ 基础

## Q37：new/delete 和 malloc/free 有什么区别？

### 推荐回答

`malloc/free` 只负责内存分配与释放。

`new/delete` 除了分配释放内存，还会调用构造函数和析构函数。

---

## Q38：shared_ptr 怎么实现？

### 推荐回答

`shared_ptr` 内部有 Control Block。

里面一般包含：

- Strong Reference Count
- Weak Reference Count

每复制一个 `shared_ptr`：

```text
strong++
```

`shared_ptr` 析构：

```text
strong--
```

当：

```text
strong == 0
```

释放对象。

当：

```text
weak == 0
```

释放 Control Block。

---

## Q39：shared_ptr 有什么问题？

### 推荐回答

典型问题是循环引用。

例如：

```text
A -> shared_ptr<B>
B -> shared_ptr<A>
```

两者引用计数永远不会变成 0。

通常一边改成 `weak_ptr`。

---

## Q40：vector push_back 会发生什么？

### 推荐回答

如果 Capacity 足够：

直接在尾部构造。

如果 Capacity 不够：

1. 分配更大的连续内存
2. 把原元素移动 / 复制过去
3. 释放旧内存

因此扩容会导致原来的：

- iterator
- pointer
- reference

失效。

---

## Q41：map 和 unordered_map 有什么区别？

### 推荐回答

`map` 一般是红黑树：

```text
查找 O(logN)
```

特点：

- 有序
- 支持范围查询
- 性能比较稳定

`unordered_map` 是 Hash Table：

```text
平均 O(1)
最坏 O(N)
```

特点：

- 无序
- 适合通过 Key 高频查找

游戏开发里如果只是频繁通过 ID 查对象，`unordered_map` 很常见。

如果需要范围查询或者有序遍历，`map` 更合适。

---

## Q42：虚函数怎么实现？

### 推荐回答

编译器通常给含虚函数的类生成 vtable。

对象内部有 vptr 指向 vtable。

通过基类指针调用虚函数时：

```text
object
  ↓
vptr
  ↓
vtable
  ↓
function
```

从而实现 Runtime Polymorphism。

---

## Q43：为什么基类析构函数应该是 virtual？

### 推荐回答

如果：

```cpp
Base* p = new Derived;
delete p;
```

Base 析构不是 virtual 时，通过 Base 指针删除可能不会正确执行 Derived 析构。

如果 Derived 持有资源，就会出现泄漏。

# 十二、图形学基础

## Q44：一个模型从 CPU 到屏幕经历什么？

### 推荐回答

主流程：

```text
CPU 提交 Draw Call
        ↓
Vertex Shader
        ↓
Primitive Assembly
        ↓
Rasterization
        ↓
Fragment / Pixel Shader
        ↓
Depth / Stencil Test
        ↓
Blend
        ↓
Frame Buffer
```

---

## Q45：什么是 Draw Call？

### 推荐回答

Draw Call 本质是 CPU 向 GPU 提交一次绘制命令。

Draw Call 多不一定说明 GPU 算力不足。

很多时候瓶颈反而在：

- CPU Submission
- Render State Change
- Pipeline State 切换

所以游戏引擎会通过：

- Batching
- Instancing
- Texture Atlas

等方式减少 Draw Call。

---

## Q46：什么条件下能 Batch？

### 推荐回答

通常至少要求：

- Shader / Material compatible
- Texture 可合并或使用 Atlas
- Render State 一致
- Blend / Depth / Stencil 状态一致

只要中间出现状态变化，就可能导致 Batch 被打断。

---

## Q47：Alpha Blend 是怎么计算的？

### 推荐回答

常见 Alpha Blend：

```text
FinalColor =
SrcColor * SrcAlpha
+
DstColor * (1 - SrcAlpha)
```

### 追问：为什么透明物体通常从后往前画？

因为 Alpha Blend 依赖已经存在于 FrameBuffer 的 Destination Color。

顺序不同，混合结果会不同。

# 十三、综合项目追问

## Q48：你最大的技术难点是什么？

### 推荐回答

我目前遇到最有挑战的一个问题是网易项目里的 2D Sprite 破坏。

难点并不是实现“挖一个洞”，而是在可接受的帧时间内稳定实现。

最初 Bitmap + 全图 Marching Squares 的方案单次会达到几十毫秒，实际游戏不可接受。

后来我从三个层面优化：

- 数据范围上用 Dirty Rect
- 拓扑上用连通域和 Island 局部重建
- 数据表示上尝试 Polygon Boolean

最终做到毫秒级。

对我影响比较大的一点是：

> 性能问题首先应该从“减少工作量”入手，而不是一开始就在某个函数里做微优化。

---

## Q49：你遇到过失败的方案吗？

### 推荐回答

倒水效果最初尝试过 Pure Shader 和 CustomMesh。

但最后发现它们分别存在形变控制、裁剪或者工程接入方面的问题。

最终没有硬坚持原方案，而是改成多层水节点加 `skewY`。

这件事让我比较明确的一点是：

> 游戏客户端开发不是寻找“技术上最炫”的方案，而是寻找视觉效果、性能、维护成本之间比较合适的方案。

---

## Q50：你简历上的性能数据是怎么测出来的？

### 推荐回答思路

这类问题不能只回答“用 Profiler 测的”。

必须准备清楚以下信息：

- 测试环境是什么
- Debug 还是 Release
- PC 还是手机
- 单次还是平均
- 测多少次
- CPU 时间还是整帧时间
- Profiling 工具是什么
- 是否控制了输入规模
- 如何保证 Before / After 可比
- 为什么确定是你的改动导致

### 推荐回答框架

我做性能对比时会尽量固定测试输入和运行环境，分别记录修改前后的 CPU 耗时、峰值 Frame Time 和调用次数。

如果是单函数热点，我会记录单次调用时间以及多次执行后的平均 / 峰值。

如果是整帧性能，则会结合 Tracy 或引擎 Profiler 查看 Frame Timeline，确认瓶颈是否确实来自目标模块。

我不会只看一次数据，而是多次运行后比较整体趋势，避免偶发抖动影响结论。

# 十四、面试风险点与准备重点

## 1. C++ 基础

你的项目和实习技术含量较高，因此如果下面这些基础题答得不好，会产生明显反差：

- vector 扩容
- 虚函数
- shared_ptr / weak_ptr
- RAII

RAII 全称 Resource Acquisition Is Initialization，是 C++ 中一种资源生命周期管理方式。核心思想是把资源的生命周期绑定到对象生命周期上：构造对象时获取资源，析构对象时释放资源。由于 C++ 的栈对象在离开作用域时会自动析构，所以即使发生 return 或异常，资源也能正确释放。

RAII 不只是管理内存，也可以管理文件、锁、Socket、GPU 资源等。像 `unique_ptr`、`shared_ptr` 和 `lock_guard` 都是典型的 RAII 应用。

它最大的价值是减少资源泄漏，并提供更好的异常安全性。

- 内存布局
- 左值 / 右值
- move
- 多线程
- 锁
- STL
