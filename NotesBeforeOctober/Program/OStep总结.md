## 1. 操作系统总览

### 1.1 操作系统解决什么问题

操作系统位于应用程序与硬件之间，主要做三件事：

1. **虚拟化**：把少量物理资源抽象成易用的虚拟资源。例如，一个 CPU 被抽象成许多进程各自拥有的“虚拟 CPU”；物理内存被抽象成每个进程独立、连续的虚拟地址空间。
2. **并发管理**：协调多个执行流，处理调度、同步、互斥、通信与死锁。
3. **持久化**：通过文件系统把易失内存中的数据可靠地保存到磁盘或 SSD。

还要同时满足：

- **方便性**：给程序提供进程、线程、文件、套接字等抽象。
- **高效性**：借助硬件直接执行、MMU、TLB、DMA、中断等机制减少开销。
- **隔离与保护**：一个程序不应随意读取或破坏另一个程序以及内核的数据。
- **公平性与可控性**：合理分配 CPU、内存和 I/O，并确保内核始终能收回控制权。

### 1.2 机制与策略

- **机制（how）**：上下文怎样切换、页表怎样完成地址转换、锁怎样原子地获取。
- **策略（which/when）**：下一步运行哪个进程、换出哪个页面、何时刷新脏页。

把二者分离，才能在不重写底层机制的情况下替换策略。例如，进程切换机制不变，调度策略可以从 FIFO 换成 MLFQ。

**面试一句话：** 操作系统通过抽象和虚拟化管理硬件资源，通过隔离保证安全，通过调度和并发控制提高利用率，并通过文件系统实现持久化。

## 2. 用户态、内核态、系统调用与中断【高频】

### 2.1 为什么要区分用户态和内核态

CPU 提供不同特权级：

- **用户态**只能执行普通指令，不能直接修改页表、关闭中断或随意访问设备。
- **内核态**可以执行特权指令并访问全部硬件资源。

这样即使应用程序出错，通常也只会终止自身，不至于破坏整个系统。

### 2.2 用户态进入内核态的三类原因

| 类型              | 来源                       | 是否与当前指令同步 | 例子                          |
| ----------------- | -------------------------- | -----------------: | ----------------------------- |
| 系统调用（trap）  | 程序主动请求               |               同步 | `read`、`write`、`fork` |
| 异常（exception） | 当前指令执行出错或特殊事件 |               同步 | 缺页、除零、非法指令          |
| 中断（interrupt） | 外部硬件                   |               异步 | 时钟、网卡、磁盘完成中断      |

有的资料把系统调用也归为软件异常。面试时先说明采用的分类即可。

### 2.3 一次系统调用发生了什么

以 `read(fd, buf, n)` 为例：

1. 应用调用 C 库包装函数，把系统调用号和参数放进约定的寄存器。
2. 执行特定陷入指令，硬件切换到内核态，保存必要的用户现场，并跳到预先注册的入口。
3. 内核校验参数和权限，根据系统调用号分派到内核中的 `read` 实现。
4. 若数据未就绪，进程可能阻塞，调度器运行别的任务；I/O 完成后由中断唤醒它。
5. 内核设置返回值，执行从陷阱返回指令，恢复用户现场并回到用户态。

系统调用看起来像普通函数调用，是因为 libc 隐藏了陷入指令；它比普通函数调用更贵，因为涉及特权级切换、参数校验以及可能的调度和缓存影响。

### 2.4 中断和异常的共同点与区别

共同点是都会暂停当前控制流，保存现场并运行处理程序。核心区别是：**中断来自当前 CPU 执行流之外，异常由当前指令触发**。时钟中断让内核即使面对不主动让出 CPU 的程序，也能重新获得控制权并实施抢占调度。

> 易错点：从用户态因中断进入内核态，不等于一定发生进程切换。内核处理完后完全可能继续运行原进程。

## 3. 进程、线程与上下文切换【高频】

### 3.1 程序与进程

- **程序**是磁盘上的静态代码和数据。
- **进程**是程序的一次运行实例，是操作系统对正在运行程序的抽象。

进程的机器状态包括：

- 地址空间：代码段、数据段、堆、栈、内存映射区。
- CPU 状态：程序计数器、栈指针、通用寄存器等。
- 内核资源：PID、状态、调度信息、打开的文件、当前目录、信号处理信息等。

内核通常用 PCB（进程控制块）保存这些信息。

### 3.2 进程状态

常见简化模型：

```text
创建 → 就绪 --被调度--> 运行 --退出--> 终止
                    运行 --等待 I/O/锁--> 阻塞
                    阻塞 --事件完成--> 就绪
                    运行 --时间片耗尽--> 就绪
```

- **就绪**：除 CPU 外条件都满足，正在排队。
- **阻塞**：在等待某事件，即使给 CPU 也不能继续。
- **运行**：当前占有 CPU。

### 3.3 线程是什么

线程是进程内部的一条执行流。同一进程的线程：

- **共享**地址空间、代码、堆、全局变量和打开的文件。
- **独有**程序计数器、寄存器、栈、线程 ID 和调度状态。

“进程是资源分配基本单位、线程是调度基本单位”是便于理解的概括，但不是跨所有系统的严格定义。更准确地说：**进程提供资源与隔离边界，内核线程通常是 CPU 调度实体。**

| 对比       | 进程     | 同一进程内的线程             |
| ---------- | -------- | ---------------------------- |
| 地址空间   | 通常独立 | 共享                         |
| 创建与切换 | 通常更重 | 通常更轻                     |
| 通信       | 需要 IPC | 可直接读写共享内存           |
| 故障隔离   | 较强     | 一个线程越界可能破坏整个进程 |
| 页表切换   | 通常需要 | 通常不需要                   |

线程切换仍需保存寄存器、PC 和栈指针。它“更轻”并不等于没有开销；调度、缓存污染和同步都可能很昂贵。

### 3.4 上下文切换发生了什么

1. 中断、异常、系统调用或主动阻塞使 CPU 进入内核。
2. 保存当前任务的寄存器等上下文。
3. 调度器选择另一个就绪任务。
4. 必要时切换地址空间和内核栈，恢复新任务上下文。
5. 返回用户态，从新任务上次停止的位置继续。

成本不仅是保存几个寄存器，还可能包括页表/TLB 处理，以及 CPU Cache、分支预测器状态不再适配新任务造成的间接损失。

### 3.5 `fork`、`exec`、`wait`【高频】

- `fork()` 创建子进程。父子进程从 `fork` 的下一条语句继续；子进程返回 0，父进程返回子进程 PID，失败返回 -1。
- 现代系统通常用 **写时复制 COW** 实现 `fork`：开始时共享只读物理页，一方写入时才触发缺页并复制。
- `exec()` 不创建新进程，而是用新程序替换当前进程的地址空间；成功后不会返回，PID 通常不变。
- `wait()/waitpid()` 回收子进程退出状态；`waitpid` 可指定子进程并支持 `WNOHANG` 非阻塞等待。

典型 Shell 执行命令：Shell `fork` 子进程，子进程用 `exec` 装载命令，父进程用 `wait` 等待；若命令以后台方式运行，Shell 不同步等待。

> 细节：`fork` 后父子拥有各自的文件描述符表，但对应描述符通常指向相同的内核 open file description，因此共享文件偏移和部分状态标志。`O_APPEND` 使每次写入定位到文件末尾与写入这一动作原子化，但多次 `write` 之间仍可能交错。

### 3.6 僵尸进程与孤儿进程

- **僵尸进程**：子进程已退出，但父进程尚未 `wait`。大部分资源已释放，只保留 PID、退出码等供父进程读取。大量僵尸会耗尽进程表项。
- **孤儿进程**：父进程先退出，仍运行的子进程会被 init/systemd 或 subreaper 接管，之后由接管者回收。

解决僵尸的根本办法是让父进程正确处理 `SIGCHLD` 并调用 `wait/waitpid`，或采用合适的进程托管机制。

## 4. CPU 调度【高频】

### 4.1 指标

- **周转时间** = 完成时间 − 到达时间，面向批处理吞吐。
- **响应时间** = 首次运行时间 − 到达时间，面向交互体验。
- 还关心吞吐量、公平性、截止时间、CPU 利用率和上下文切换成本。

### 4.2 常见算法

| 算法          | 思想                         | 优点                                         | 主要问题                              |
| ------------- | ---------------------------- | -------------------------------------------- | ------------------------------------- |
| FCFS/FIFO     | 先到先运行                   | 简单                                         | 长任务造成护航效应                    |
| SJF           | 先运行最短任务               | 所有任务同时到达且时长已知时平均周转时间最优 | 时长难预测，长任务可能饥饿            |
| SRTF          | 抢占式 SJF，选剩余时间最短者 | 对短任务响应好                               | 同上，切换更多                        |
| RR            | 每个任务运行一个时间片       | 公平、响应好                                 | 时间片太短则切换多，太长则退化为 FIFO |
| 优先级调度    | 高优先级先运行               | 可表达业务重要性                             | 低优先级可能饥饿，可用老化缓解        |
| 彩票/步长调度 | 按票数实现比例份额           | 彩票简单灵活；步长更确定                     | 彩票有随机波动；步长需维护全局状态    |

### 4.3 多级反馈队列 MLFQ

目标是在不知道任务运行时长的情况下，同时照顾短任务和交互任务：

1. 多个不同优先级队列；只要高优先级队列非空，就不运行低优先级队列。
2. 同级任务通常 RR。
3. 新任务进入最高优先级。
4. 用完某级累计时间配额则降级；主动阻塞的交互任务通常保留较高优先级。
5. 周期性把所有任务提升到最高级，避免饥饿并适应任务行为改变。

关键改进是按**累计配额**降级，防止程序在时间片快结束前主动让出 CPU 来欺骗调度器。

### 4.4 多核调度

- **单运行队列**简单、易做全局负载均衡，但共享队列锁会限制扩展性，任务也可能在核心间迁移而损失缓存亲和性。
- **每核队列**锁竞争少、缓存亲和性好，但可能负载不均，需要任务迁移或工作窃取。
- 调度器要权衡负载均衡与缓存亲和性；迁移太频繁也会降低性能。

> 面试例子：CPU0 的队列有 10 个任务，CPU1 已空闲。若坚持亲和性，CPU1 被浪费；若迁移一个任务，可以均衡负载，但该任务需要在 CPU1 重建缓存。工作窃取就是让空闲核心偶尔从繁忙核心取任务。

## 5. 进程间通信 IPC【高频】

IPC 的本质是让相互隔离的进程传递数据、状态或控制信息。

| 方式               | 数据路径与特点                                                  | 典型场景/注意点                          |
| ------------------ | --------------------------------------------------------------- | ---------------------------------------- |
| 匿名管道           | 内核中的字节流缓冲区，通常单向；常在`fork` 后的亲缘进程间使用 | Shell 管道；无消息边界                   |
| FIFO/命名管道      | 文件系统中有名字，可供无亲缘进程打开                            | 本机简单通信；仍是字节流                 |
| 消息队列           | 内核维护有边界、可带类型的消息                                  | 异步传递；有内核复制和容量限制           |
| 共享内存           | 多进程页表映射同一物理页                                        | 本机大数据量最快；必须另做同步           |
| 信号               | 异步事件通知，承载信息很少                                      | 终止、定时器、子进程退出；处理函数限制多 |
| 信号量             | 计数型同步原语，主要协调资源而非传数据                          | 进程或线程同步                           |
| Unix Domain Socket | 本机双向通信，可传字节流/数据报及文件描述符                     | 客户端-服务端，接口统一                  |
| TCP/UDP Socket     | 可跨主机、双向                                                  | 分布式系统；需要协议设计                 |

### 5.1 管道的关键语义

`pipe(fd)` 得到 `fd[0]` 读端和 `fd[1]` 写端。父子进程应关闭不使用的一端，否则可能导致读者永远等不到 EOF。

- 管道空且仍有写端打开时，阻塞式 `read` 等待。
- 所有写端关闭后，读完剩余数据的 `read` 返回 0（EOF）。
- 所有读端关闭后继续写，进程通常收到 `SIGPIPE`，`write` 返回 `EPIPE`。
- 小于等于 `PIPE_BUF` 的一次写入具有不与其他写者交错的原子性保证，但管道整体没有消息边界。

### 5.2 为什么共享内存快

建立映射时需要进入内核，但建立后通信双方直接读写同一物理内存，避免每条消息在用户态和内核态之间反复复制。代价是双方必须用锁、信号量或原子操作保证一致性，并约定数据布局和生命周期。

**选择思路：** 少量通知用信号；有消息边界用消息队列/数据报；大数据量本机通信用共享内存；需要通用双向或跨机器通信用 Socket。

## 6. 并发、原子性与锁【高频】

### 6.1 并发与并行

- **并发**：多个任务在同一时间段内推进，单核交替执行也可以并发。
- **并行**：多个任务在同一时刻由多个处理单元真正同时执行。

并发问题并不要求多核才出现：单核上的抢占也能在任意指令间打断线程。

### 6.2 竞态条件示例

`counter++` 通常不是一条原子指令，而是“读入寄存器 → 加一 → 写回”。若两个线程都先读到 50，再分别写回 51，最终结果是 51 而不是 52，这叫**丢失更新**。

- **临界区**：访问共享可变状态、不能让多个线程任意交错的代码。
- **互斥**：同一时刻至多一个线程处于相关临界区。
- **原子性**：操作对其他线程表现为不可分割，要么尚未发生，要么已经全部完成。
- **竞态条件**：结果依赖不可控的执行时序。

除原子性外，并发还涉及**可见性**和**有序性**。编译器、CPU 和缓存可能重排或延迟传播内存操作。应使用语言/平台提供的原子类型、锁和内存序，不能把 `volatile` 当作通用线程同步工具。

### 6.3 锁应满足什么

1. **正确性**：真正互斥。
2. **活性与公平性**：最好避免饥饿。
3. **性能**：无竞争时开销小，有竞争时不过度浪费 CPU，并能扩展到多核。

锁只保护它约定保护的数据；正确性依赖所有访问者遵守同一协议。临界区应尽量短，避免在持锁期间做慢 I/O、等待另一个线程或调用不可控代码。

### 6.4 锁的硬件基础

普通的“检查 `flag==0`，再设为 1”会在两步之间被打断。硬件因此提供原子读-改-写指令：

- test-and-set / xchg
- compare-and-swap（CAS）
- fetch-and-add
- load-linked/store-conditional（LL/SC）

以 CAS 为例：仅当内存仍等于期望旧值时才写入新值，并返回是否成功。CAS 可构建自旋锁和许多无锁结构，但还需处理 ABA、内存回收、内存序等问题；“用了 CAS”不自动等于正确。

### 6.5 自旋锁、互斥锁与 futex

- **自旋锁**：拿不到锁时循环检查，不发生睡眠切换。适合多核、临界区极短、不能睡眠的场合；竞争激烈或单核持锁线程被抢占时浪费巨大。
- **互斥锁**：竞争时可让线程睡眠，适合等待可能较长的场合，但阻塞和唤醒有系统调用与调度开销。
- **两阶段/自适应锁**：先短暂自旋，仍拿不到再睡眠，试图兼得两者优势。
- Linux `futex` 常走“无竞争时纯用户态原子操作，有竞争时进入内核休眠/唤醒”的路径。

> 不能简单说“自旋锁一定比互斥锁快”。判断关键是临界区长度、竞争程度、CPU 数量以及持锁线程是否可能被抢占。

### 6.6 锁粒度

- 粗粒度锁：实现简单、容易正确，但并发度低。
- 细粒度锁：可并行访问不同数据，但锁数量、顺序和开销上升，死锁风险更高。

例如散列表可以每个桶一把锁，不同桶并行；链表每个节点一把“过手锁”理论并发度更高，但遍历时频繁加解锁可能反而更慢。**并发度更高不等于性能更高，最终要测量。**

### 6.7 读写锁

读写锁允许多个读者并发，但写者需要独占。它适合读多写少且读临界区不太短的情况；否则维护读者数和公平性的成本可能超过收益。策略偏向读者会饿死写者，偏向写者也可能增加读延迟。

## 7. 条件变量与信号量【高频】

### 7.1 条件变量解决什么问题

锁解决“同一时刻谁能访问”，条件变量解决“条件不满足时怎样高效等待”。条件变量本质上是等待队列，必须配合一个受互斥锁保护的**状态谓词**使用。

标准模式：

```c
pthread_mutex_lock(&mutex);
while (!condition)                 // 必须重新检查
    pthread_cond_wait(&cond, &mutex);
use_shared_state();
pthread_mutex_unlock(&mutex);
```

修改状态的一方：

```c
pthread_mutex_lock(&mutex);
change_shared_state();
pthread_cond_signal(&cond);        // 或 broadcast
pthread_mutex_unlock(&mutex);
```

`wait` 会**原子地释放锁并睡眠**；醒来后先重新获得锁才返回。原子性避免“检查完条件、准备睡眠的间隙，对方已经发出通知”造成永久睡眠。

为什么用 `while` 而不是 `if`：

1. 可能虚假唤醒。
2. 从被唤醒到真正重新获得锁之间，另一个线程可能已改变条件。
3. 唤醒只表示“状态可能变化”，不承诺条件现在一定为真。

`signal` 通常唤醒一个等待者，`broadcast` 唤醒全部。无法确定哪个等待者能满足条件时可用 broadcast，但会产生“惊群”。

### 7.2 生产者—消费者

有界缓冲区容量为 `N` 时，需要：

- 一把互斥锁保护缓冲区、读写索引和计数。
- `not_full`：生产者等待“缓冲区未满”。
- `not_empty`：消费者等待“缓冲区非空”。

生产者在锁内用 `while (count == N)` 等待，放入元素后通知 `not_empty`；消费者在锁内用 `while (count == 0)` 等待，取出后通知 `not_full`。等待动作会临时释放锁，因此消费者睡眠时不会妨碍生产者填充数据。

### 7.3 信号量

信号量是带整数计数的同步原语：

- `wait/P/down`：尝试消耗一个许可，没有许可则等待。
- `post/V/up`：增加一个许可，必要时唤醒等待者。

典型初始化：

- 初值 1：可作为二值信号量实现互斥。
- 初值 0：可表达先后顺序，例如父线程等待子线程完成事件。
- 初值 N：表示最多 N 个线程可同时使用某类资源。

条件变量没有“通知记忆”：无人等待时 signal 通常就过去了；信号量的 post 会保留为计数。条件变量围绕任意状态谓词，信号量本身就是状态/许可数。

有界缓冲区也可用 `empty=N`、`full=0` 和 `mutex=1` 三个信号量实现。必须先等待 `empty/full`，再进入受 `mutex` 保护的短临界区；若消费者拿着 mutex 再等待 full，而生产者又需要 mutex 才能生产，就会死锁。

### 7.4 常见并发 Bug

- **非死锁类**：原子性违反、顺序违反、可见性问题。
- **死锁**：互相等待且永远无法推进。
- **活锁**：线程都在运行并反复让步，但系统没有进展。
- **饥饿**：某线程长期得不到 CPU、锁或资源。
- **优先级反转**：高优先级线程等待低优先级持有的锁，而中优先级线程又持续抢占低优先级线程；可用优先级继承缓解。

## 8. 死锁【高频】

### 8.1 四个必要条件

死锁同时需要：

1. **互斥**：资源不能共享。
2. **请求并保持**：持有部分资源时继续等待其他资源。
3. **不可剥夺**：资源只能由持有者主动释放。
4. **循环等待**：等待关系形成环。

它们是必要条件，破坏任意一个即可预防死锁。

> 示例：线程 A 持有 L1 等 L2，线程 B 持有 L2 等 L1。二者都不释放已有锁，形成环路。

### 8.2 处理策略

- **预防**：统一锁顺序破坏循环等待；一次申请全部资源破坏请求并保持；允许回滚/抢占。
- **避免**：分配前判断是否仍处于安全状态，经典算法是银行家算法。需要预知最大需求，通用系统较少使用。
- **检测与恢复**：允许发生，周期性构建等待图检测环，再终止/回滚任务。
- **忽略**：死锁少见且处理代价高时，由应用超时、重启或人工处理；通用 OS 对许多资源采用这种务实策略。

工程中最实用的是：固定全局加锁顺序、缩小临界区、避免持锁等待外部事件、使用带超时的获取、通过工具检测锁依赖。

哲学家就餐中，若每个人都先拿左叉再等右叉就会形成环。让其中一人按相反顺序取叉，或按叉编号从小到大获取，都能破坏循环等待。

## 9. 虚拟内存与地址转换【高频】

### 9.1 地址空间的目标

每个进程看到独立、连续、从固定位置开始的虚拟地址空间，实际物理页可以离散地分布。目标是：

- **透明**：程序通常不关心物理位置。
- **高效**：地址转换由 MMU 和 TLB 加速。
- **保护**：进程不能越权访问其他进程或内核。
- **灵活**：支持稀疏空间、共享页、按需分配和超过物理内存的地址空间。

### 9.2 从基址/界限到分段

最简单的动态重定位：

```text
物理地址 = 基址寄存器 + 虚拟地址
同时检查 0 <= 虚拟地址 < 界限
```

它能移动和隔离整个地址空间，但要求空间连续，内部空洞浪费大。

分段为代码、堆、栈等逻辑段分别设置基址、界限和权限，支持共享与不同增长方向，但不同大小的段会造成**外部碎片**：总空闲空间足够，却没有足够大的连续块。内存紧凑可解决，但搬移成本高。

### 9.3 分页

分页把虚拟空间分成固定大小的**页**，物理内存分成同样大小的**页框/页帧**。页表记录虚拟页号 VPN 到物理页框号 PFN 的映射。

假设虚拟地址 16 位、页大小 4 KiB：

- 页内偏移占 `log2(4096)=12` 位。
- VPN 占 4 位。
- 若虚拟地址是 `0x3123`，则 VPN=`0x3`，offset=`0x123`。
- 若页表给出 VPN 3 → PFN `0xA`，物理地址就是 `0xA123`。

**页内偏移在转换前后不变。**

常见 PTE 信息：

- 有效/映射位：虚拟页是否属于合法地址空间。
- 存在位：页当前是否在物理内存。
- PFN 或换出位置。
- 读/写/执行权限，用户/内核权限。
- accessed/reference 位：是否被访问。
- dirty 位：载入后是否被写过。

> “有效”和“存在”要区分：合法但不在内存会触发可处理的缺页；地址根本不合法或权限不符通常导致进程收到 `SIGSEGV` 等错误。

### 9.4 页的碎片问题

- 分段/可变大小连续分配容易产生**外部碎片**。
- 分页没有页框之间的外部碎片，但最后一页未用满会产生**内部碎片**。
- 大页可减少页表项和 TLB 压力，适合大内存工作集；代价是内部碎片、分配困难和管理复杂。

### 9.5 多级页表

单级线性页表会为大量未使用虚拟地址也预留 PTE。例如 32 位地址、4 KiB 页、每个 PTE 4 B：每进程页表约 4 MiB。

多级页表把页表自身也分页，只为实际使用的地址区域分配下级页表：

```text
虚拟地址 = 页目录索引 | 下级页表索引 | 页内偏移
页目录 → 找到下级页表 → 找到 PTE → 得到 PFN
```

优点是适合稀疏地址空间、按需分配；缺点是 TLB 未命中时要多次访问内存。现代 64 位系统通常使用更多级页表。

### 9.6 TLB【高频】

TLB 是 MMU 中缓存“VPN → PFN”转换结果的小型高速缓存。

- TLB 命中：直接得到 PFN，再访问目标内存。
- TLB 未命中：硬件或内核遍历页表，把映射填入 TLB，然后重试指令。
- **TLB 未命中不等于缺页**：未命中只表示转换不在 TLB；页表可能立即给出在内存中的有效映射。
- 上下文切换时可清空 TLB，或用 ASID/PCID 标记映射属于哪个地址空间，减少刷新。

数组顺序访问命中率高，是因为同一页内后续元素复用一次转换（空间局部性）；不久后再访问同一页又利用时间局部性。

### 9.7 一次内存访问的完整路径

1. CPU 产生虚拟地址，拆成 VPN 和 offset。
2. 查 TLB；命中则得到 PFN。
3. 未命中则查多级页表：
   - 映射合法且页在内存：填充 TLB，重试。
   - 映射合法但页不在内存：触发 page fault。
   - 映射非法或权限不符：异常，内核通常向进程发送信号。
4. 用 `PFN | offset` 形成物理地址，再通过 CPU Cache/内存层次访问数据。

## 10. 缺页、页面置换与写时复制【高频】

### 10.1 按需分页与缺页处理

按需分页只在真正访问页面时载入它。一次合法缺页大致经历：

1. 硬件发现 PTE 的存在位为 0，触发异常并陷入内核。
2. 内核检查该虚拟地址是否合法、访问权限是否允许。
3. 找到空闲页框；若没有，选择牺牲页。
4. 脏牺牲页需要写回；干净且有文件后备的页可直接丢弃。
5. 从文件/交换区读入页面，或为匿名页分配并清零。
6. 更新 PTE，必要时使旧 TLB 项失效，然后重试原指令。

磁盘 I/O 期间当前进程阻塞，CPU 可运行其他就绪进程。

### 10.2 页面置换

| 算法                | 思想                   | 特点                       |
| ------------------- | ---------------------- | -------------------------- |
| OPT                 | 换出未来最晚使用的页   | 理论最优，只能用于比较     |
| FIFO                | 换出最早进入的页       | 简单，可能出现 Belady 异常 |
| Random              | 随机换出               | 简单，避免某些极端序列     |
| LRU                 | 换出最长时间未使用的页 | 利用局部性，精确实现昂贵   |
| Clock/Second Chance | 用访问位近似 LRU       | 实用、开销较低             |

Clock 算法循环检查页面：访问位为 1 就清零并跳过；遇到 0 则选择换出。还可优先选择未访问且干净的页，因为脏页需要写回。

页面未命中可分为冷启动/强制未命中、容量未命中和硬件 Cache 中的冲突未命中。操作系统页缓存通常可把任意页放入任意页框，因此一般不把它归为集合映射导致的冲突未命中。

### 10.3 抖动与工作集

进程活跃使用的一组页面称为工作集。若所有运行进程的工作集总量明显超过物理内存，系统会把时间大量耗在换入换出上，CPU 利用率反而下降，这就是**抖动**。

缓解方法包括减少并发进程、按工作集分配内存、增加物理内存、限制容器/进程内存；极端内存不足时 Linux 可能触发 OOM Killer。

### 10.4 写时复制 COW

`fork` 时不立即复制所有物理页，而让父子页表都指向同一批只读页。只读访问一直共享；一方写入触发保护异常，内核分配新页、复制内容，再把写入方映射到私人副本。

收益是降低 `fork` 延迟和内存占用，尤其适合子进程马上 `exec` 的场景。类似的惰性思想还有按需置零和按需加载。

### 10.5 `mmap` 与页缓存

`mmap` 把文件或匿名对象映射进地址空间，访问映射就像访问内存，首次触碰可能缺页。文件映射通常与内核页缓存统一：

- `MAP_SHARED` 的修改可对其他映射者可见并最终写回文件。
- `MAP_PRIVATE` 通常使用 COW，修改不会写回原文件。

它不是“永远比 read/write 快”；性能取决于访问模式、缺页成本、数据复制、预读和错误处理需求。

## 11. 动态内存分配【中频】

### 11.1 栈与堆

- 栈上对象通常随函数调用自动分配和回收，速度快，但生命周期受作用域/调用约束，每线程有自己的栈。
- 堆由 `malloc/free` 等显式管理，生命周期灵活，但可能有碎片、泄漏和并发开销。

`malloc/free` 是库函数，不是系统调用。分配器会从已向内核取得的大块虚拟内存中切分小块，必要时通过 `brk/sbrk` 或 `mmap` 扩展。

### 11.2 分配器怎样知道 `free(ptr)` 的大小

常见做法是在返回给用户的块之前放置隐藏头部，记录块大小和状态。`free` 根据 `ptr` 找到头部，再把块放回空闲结构，并尝试与相邻空闲块合并。

常见策略：

- first fit：第一个够大的块，快但前部易残留小洞。
- best fit：最小的可用块，搜索成本高，也可能制造很多极小碎片。
- segregated list：不同大小类别维护不同空闲链表。
- buddy：按 2 的幂递归拆分，伙伴空闲时快速合并；可能有内部碎片。
- 内核常在伙伴系统之上使用 slab/slub 缓存固定类型的小对象，减少初始化和碎片开销。

### 11.3 常见内存错误

- 未分配就写、越界、分配少一个字符串结尾 `\0`。
- use-after-free、double free、悬空指针。
- 内存泄漏、未初始化读取。
- 返回指向已结束线程/函数栈帧中局部变量的指针。

进程退出后 OS 会回收其整个地址空间，所以短命进程退出时泄漏的物理资源会被回收；但长期服务中的泄漏会持续增加工作集，并可能导致抖动或 OOM。

## 12. I/O、多路复用与文件系统【高频补充】

原笔记的“持久化”部分为空，本章补齐计算机岗位常问内容。

### 12.1 I/O 的基本路径

以磁盘读取为例：

1. 进程通过系统调用提交请求。
2. 内核检查页缓存；命中则可直接返回。
3. 未命中时文件系统把文件偏移转换为块位置，块层和设备驱动提交请求。
4. 设备通过 DMA 在设备与内存之间搬运数据，CPU 不必逐字节复制。
5. 完成后设备产生中断，内核唤醒等待进程。

缓存、缓冲和异步提交的目的，是弥合 CPU、内存和设备之间巨大的速度差。

### 12.2 阻塞、非阻塞、同步、异步

这是两组不同维度：

- **阻塞/非阻塞**关注一次调用在暂时不能完成时，线程是否睡眠等待。
- **同步/异步**关注 I/O 完成是否需要调用方继续主动等待/查询，以及完成结果如何交付。

非阻塞 I/O 的 `read` 若当前无数据，会立即返回 `EAGAIN`；它不等于异步 I/O，因为真正的数据读取通常仍由应用在“就绪”后调用 `read` 完成。

### 12.3 `select`、`poll`、`epoll`【高频】

它们监视的是文件描述符的**就绪状态**，不是帮应用完成业务处理。

| 机制       | 描述符组织                 | 每次等待成本               | 主要特点                            |
| ---------- | -------------------------- | -------------------------- | ----------------------------------- |
| `select` | 位图                       | 每次复制集合并线性扫描     | 有`FD_SETSIZE` 限制，会修改集合   |
| `poll`   | `pollfd` 数组            | 每次复制并线性扫描         | 无固定小上限，仍随监视数增长        |
| `epoll`  | 内核维护兴趣集合与就绪队列 | 注册和等待分离，返回就绪项 | 适合大量连接中少量活跃的 Linux 场景 |

不要绝对地回答“epoll 永远 O(1)”。事件注册、回调、就绪队列、描述符处理都有成本；它的关键优势是避免每次把完整集合交给内核并线性返回所有描述符。

### 12.4 LT 与 ET

- **水平触发 LT**：只要 fd 仍然就绪就会继续通知，较容易编程。
- **边缘触发 ET**：通常只在状态从未就绪变为就绪时通知，事件更少，但必须使用非阻塞 fd，并循环读取/写入直到 `EAGAIN`，否则可能遗留数据却等不到新边缘。

典型 epoll 服务器：accept socket 设为非阻塞并注册；收到连接事件后循环 `accept` 到 `EAGAIN`；收到读事件后循环 `read` 到 `EAGAIN`；解析请求后处理并关注写就绪。业务计算仍可能需要线程池，不能让事件循环执行长时间阻塞任务。

### 12.5 零拷贝

“零拷贝”通常是减少而非字面消灭全部拷贝。传统“读文件再发 Socket”可能经历磁盘 → 内核页缓存 → 用户缓冲区 → Socket 内核缓冲区 → 网卡。`sendfile` 可让数据主要在内核路径中传递，减少用户态/内核态切换和 CPU 数据复制；DMA 仍会在设备与内存间搬运。

### 12.6 文件描述符、打开文件表与 inode【高频】

一次 `open` 后：

```text
进程的 fd 表项 → 内核打开文件对象 → inode/vnode → 数据块
                         └→ 当前文件偏移、状态标志
```

- fd 是进程内的小整数索引，不是文件本身。
- `dup` 或 `fork` 后的描述符可指向同一打开文件对象，因此共享文件偏移。
- 不同的独立 `open` 通常产生不同打开文件对象和独立偏移，但可指向同一 inode。
- inode 保存文件类型、权限、所有者、大小、时间和数据块位置等元数据，通常不保存文件名；目录项建立“文件名 → inode”的映射。

### 12.7 硬链接与软链接

- **硬链接**是另一个目录项，指向同一 inode。删除一个名字只是减少链接计数；链接数为 0 且没有进程打开时，数据才真正回收。通常不能跨文件系统，也通常不允许普通用户给目录创建硬链接。
- **软链接**是一个特殊文件，内容是目标路径。可跨文件系统、可指向目录，也可能成为悬空链接。

为什么“删除正在被使用的日志文件，磁盘空间没释放”：目录项虽被删，但进程仍持有打开文件对象；关闭 fd 后 inode 和数据块才可回收。可用 `lsof` 类工具定位。

### 12.8 页缓存、缓冲写与 `fsync`

普通 `write` 往往先把数据写入内核页缓存并标脏，很快就返回，内核稍后回写设备。因此：

- `write` 成功不等于数据已落到持久介质。
- `fsync(fd)` 请求把该文件相关数据及必要元数据推进到稳定存储；目录项创建/重命名的持久性还常需同步目录。
- `close` 通常不等价于 `fsync`。
- 设备自身缓存、控制器与文件系统实现都会影响真正的持久性语义。

### 12.9 崩溃一致性与日志

创建文件可能需要更新 inode、位图、目录项等多个位置。若更新一半时断电，文件系统会不一致。

**预写日志（WAL/journaling）**的核心是：先把即将进行的更新作为事务写入日志并提交，再更新正式位置；崩溃恢复时根据完整日志重放。不同模式可能只记录元数据，或同时记录数据。日志解决文件系统内部一致性，不自动保证应用多个文件/多次写入的业务事务语义。

Copy-on-Write 文件系统则把修改写到新位置，最后原子切换根指针，并可结合校验和、快照提高可靠性。

### 12.10 HDD、SSD 与 RAID 概览

- HDD 随机 I/O 受寻道和旋转延迟影响大，顺序大块传输更高效。
- SSD 无机械寻道，但有擦除块、写放大、磨损均衡和垃圾回收；TRIM 告知哪些逻辑块可回收。
- RAID 0 条带化：性能/容量高，无冗余。
- RAID 1 镜像：可容忍副本故障，容量利用率低。
- RAID 5 分布式单校验：容忍一块盘故障，小写有读改写惩罚。
- RAID 6 双校验：可容忍两块盘故障，写入代价更高。
- RAID 10 镜像后条带化：性能与可靠性较好，容量成本高。

RAID 不是备份：误删、勒索软件、逻辑损坏可同步影响全部副本。

## 13. 高频面试问答速记

### 13.1 进程与调度

**Q1：进程和线程的区别？**

进程是资源和隔离边界，拥有独立地址空间；线程是进程内执行流，共享地址空间和文件等资源，但各有寄存器、PC 和栈。线程创建与切换通常更轻，通信方便，但隔离差且需要同步。

**Q2：进程切换一定比线程切换慢吗？**

通常同进程线程切换少了地址空间切换，成本较低，但不能绝对化。实际成本受是否跨核、TLB 的 ASID/PCID、缓存工作集、调度路径等影响。

**Q3：`fork` 为什么返回两次，`exec` 为什么不返回？**

`fork` 创建了两个从同一位置继续的执行流，通过不同返回值区分父子；成功的 `exec` 已把当前程序替换，新程序从入口执行，不再回到旧调用点。

**Q4：僵尸进程占不占内存？**

其用户地址空间等主体资源已释放，但仍占 PID 和进程表中的退出状态记录，直到父进程回收。

**Q5：什么时候发生上下文切换？**

时间片耗尽、更高优先级任务就绪、当前任务阻塞、主动让出或退出时可能切换。进入内核态不必然切换任务。

**Q6：调度中响应时间和周转时间为何冲突？**

频繁轮转和偏爱短任务能改善响应，但增加切换并可能延长长任务完成时间；批处理追求周转/吞吐，交互系统更看重响应与公平。

### 13.2 内存

**Q7：虚拟内存有什么好处？**

提供隔离和权限保护、连续且更大的地址空间、按需分配、共享页与 COW，并简化程序装载和内存管理。

**Q8：TLB 未命中和缺页有什么区别？**

TLB 未命中只说明高速转换缓存里没有映射，查页表即可解决；缺页说明页表显示页面当前不在物理内存或访问触发了特殊映射处理，需内核分配/调入页面。前者常是纳秒级附近的额外页表访问，后者若访问磁盘可能慢几个数量级。

**Q9：为什么页表要多级？**

虚拟空间很大且稀疏，单级页表会为未使用区域浪费大量内存；多级页表只为使用到的区域分配下级表，代价是 TLB 未命中时遍历次数增加。

**Q10：什么是缺页异常？一定是错误吗？**

不是。按需加载、栈增长、COW 和 mmap 首次访问都会用缺页异常完成正常工作。只有地址非法或权限不允许且内核无法修复时，才通常向进程报告段错误。

**Q11：内部碎片和外部碎片？**

内部碎片是已分配单元内部未使用空间，例如一页只用一部分；外部碎片是空闲空间被切成不连续小洞，总量够但无法满足连续大块请求。

**Q12：为什么大页可能更快？**

同样数量的 TLB 项可覆盖更大地址范围，减少 TLB 未命中和页表规模；代价是内部碎片、分配与迁移困难。

**Q13：`malloc` 分配的是物理内存吗？**

通常先从用户态分配器管理的虚拟地址区间返回一块；即使向内核扩展了映射，物理页也常在首次访问时按需分配，因此 `malloc` 成功不代表相应物理页都已就位。

### 13.3 并发

**Q14：互斥锁和自旋锁如何选择？**

等待极短、运行在多核且上下文不允许睡眠时可自旋；等待可能较长或竞争激烈时应阻塞。还需考虑持锁线程会不会被抢占，实践中常用先自旋后睡眠的混合方式。

**Q15：条件变量为什么必须搭配锁，为什么用 while？**

锁保护条件所依赖的共享状态，`wait` 原子释放锁并睡眠以防丢失唤醒；醒来时条件可能已被别人改变或发生虚假唤醒，所以必须 while 重检。

**Q16：信号和信号量区别？**

信号是面向进程的异步事件通知；信号量是带计数的同步原语，用于互斥、资源许可或执行顺序。二者名字相似，机制和用途不同。

**Q17：互斥锁和信号量区别？**

互斥锁强调所有权：通常由加锁者解锁，用于保护不变量；信号量表示许可数，post 不一定由 wait 者执行，可用于资源计数和事件同步。能用信号量模拟锁，不代表语义上应混用。

**Q18：CAS 有什么问题？**

高竞争下反复重试浪费 CPU；还涉及 ABA、缓存行争用、内存序以及无锁结构的安全内存回收。无锁通常意味着系统整体持续推进，不保证每个线程都不饥饿。

**Q19：死锁、活锁、饥饿区别？**

死锁是彼此等待且都阻塞；活锁是都在活动但互相退让而无进展；饥饿是某个任务长期得不到资源，其他任务仍能推进。

**Q20：如何避免死锁？**

最常用是统一锁顺序，避免持锁做阻塞操作，缩短临界区，必要时 try-lock/超时后释放重试，并用锁依赖工具检测。

### 13.4 I/O 与文件系统

**Q21：select、poll、epoll 的区别？**

select 用位图且有大小限制，poll 用数组取消小上限，但两者每轮都需传入并扫描完整集合；epoll 把兴趣集合留在内核，等待时主要返回就绪项，更适合大量连接少量活跃。连接少且始终活跃时，差距未必大。

**Q22：ET 为什么必须读到 EAGAIN？**

ET 主要在状态变化的边缘通知。如果一次只读一部分，缓冲区仍有数据但状态没有产生新边缘，应用可能长时间不再收到通知。

**Q23：零拷贝零在哪里？**

通常指避免数据经过用户缓冲区以及减少 CPU 拷贝和模式切换，并非数据从磁盘到网卡完全不搬运；DMA 仍会搬运，协议栈也仍有元数据处理。

**Q24：`write` 返回成功后断电，数据一定存在吗？**

不一定。数据可能只在页缓存或设备易失缓存中。需要根据文件系统语义正确调用 `fsync/fdatasync`，并考虑目录元数据和存储设备的持久化保证。

**Q25：文件名存在哪里？inode 存什么？**

文件名在目录项中，目录项映射到 inode；inode 保存文件元数据和数据块位置，通常不保存文件名。因此同一 inode 可以有多个硬链接名字。

**Q26：删除文件为什么不影响已经打开它的进程？**

`unlink` 删除名字并减少链接计数，打开的 fd 仍引用该内核文件对象/inode。最后一个引用关闭后才回收数据。

**Q27：共享内存为什么还需要锁？**

它只解决“双方看到同一数据”，不保证复合读写的原子性、顺序和一致性。多个执行流更新共享结构仍会竞态。

**Q28：同步 I/O、异步 I/O、I/O 多路复用是什么关系？**

多路复用让一个线程等待多个 fd 的就绪事件；就绪后通常仍由应用同步调用 read/write。真正异步 I/O 是提交请求后由内核完成，并通过完成事件、回调等交付结果。

### 检查表参考答案

以下答案采用“先给结论，再讲机制，最后补充边界”的面试口述方式。实际面试时可根据追问深度适当缩短或展开。

#### 1. 用一分钟说明操作系统的四条主线

操作系统位于应用程序和硬件之间，核心工作可以概括为四条主线：

1. **CPU 虚拟化**：通过进程、线程、时钟中断和调度，让多个程序分时共享少量 CPU，同时让每个程序感觉自己在独立运行。
2. **内存虚拟化**：通过虚拟地址、页表、MMU 和 TLB，为每个进程提供独立、连续且受保护的地址空间，并通过按需分页支持大于物理内存的虚拟空间。
3. **并发控制**：多个执行流会共享资源，操作系统和运行库用锁、条件变量、信号量、原子指令等机制解决竞态、同步、死锁和可见性问题。
4. **持久化**：文件系统把易失内存中的数据组织成文件和目录，通过页缓存、块设备、日志或 COW 等机制写入磁盘，并在崩溃后维持一致性。

贯穿四条主线的共同目标是：**抽象硬件、提高利用率，同时保证隔离、保护、性能和可靠性。**

#### 2. 画出进程状态图，说明阻塞与就绪的区别

```text
                 时间片用完/被抢占
              ┌───────────────────┐
              ▼                   │
创建 ───────→ 就绪 ──被调度────→ 运行 ─────→ 终止
              ▲                   │
              │                   │ 等待 I/O、锁或事件
              │    事件完成       ▼
              └───────────────── 阻塞
```

- **就绪态**：运行需要的资源基本齐全，只缺 CPU；只要调度器选中就能立即运行。
- **阻塞态**：正在等待 I/O、锁、条件变量或其他事件；即使立刻分配 CPU 也不能继续。
- 运行进程时间片耗尽会回到就绪态；运行进程发起阻塞 I/O 会进入阻塞态；事件完成后只是从阻塞变成就绪，还要等待调度才能运行。

#### 3. 讲清 `fork → exec → wait`，以及 COW、僵尸、孤儿进程

典型场景是 Shell 启动外部命令：

1. Shell 调用 `fork()` 创建子进程。父子从 `fork` 后继续执行；子进程看到返回值 0，父进程得到子进程 PID。
2. 子进程可先重定向文件描述符，再调用 `exec()`。`exec` 不创建进程，而是用目标程序的代码、数据、堆和栈替换当前地址空间；PID 通常不变，成功后不会返回旧程序。
3. 父进程调用 `wait/waitpid` 等待并读取退出状态，同时回收内核保留的子进程表项。

`fork` 在语义上给父子提供相互独立的地址空间，但现代系统通常采用 **写时复制 COW**：父子开始共享只读物理页，只有一方写入时才触发异常并复制该页，所以“逻辑独立”不等于“立即完整物理复制”。

- 子进程已退出而父进程尚未 `wait`，它是**僵尸进程**。用户内存已释放，但 PID 和退出状态等表项仍保留。
- 父进程先退出而子进程仍运行，子进程成为**孤儿进程**，会由 init/systemd 或 subreaper 接管并负责回收。

#### 4. 比较进程与线程，并说明上下文切换真正贵在哪里

进程通常是资源和隔离边界，拥有独立虚拟地址空间；线程是进程内的执行流。同一进程内的线程共享代码、堆、全局变量和打开的文件，但各有程序计数器、寄存器、栈和调度状态。

进程隔离强，故障通常不会直接破坏其他进程，但通信需要 IPC；线程共享数据方便、创建和切换通常更轻，却需要同步，一个线程非法写内存可能破坏整个进程。

上下文切换的直接工作包括进入内核、保存旧任务寄存器、运行调度器、恢复新任务寄存器和返回用户态。进程切换通常还要切换地址空间；线程在同一进程内切换通常不用换页表。但更大的隐藏成本来自：

- 新任务的代码和数据不在 CPU Cache 中。
- TLB 可能需要刷新，或虽然有 ASID/PCID 仍出现更多未命中。
- 分支预测器、预取器等微架构状态不再适配。
- 任务迁移到另一个 CPU 后失去缓存亲和性。

因此不能只用“保存几个寄存器”估算切换成本，也不能绝对断言任意线程切换都一定比任意进程切换快。

#### 5. 比较 FCFS、SJF/SRTF、RR、MLFQ，说明饥饿与老化

- **FCFS/FIFO**按到达顺序运行，简单且无抢占，但一个长任务会让后面的短任务等待，产生护航效应。
- **SJF**选择预计运行时间最短的任务；当任务同时到达且时长已知时，平均周转时间最优。现实中运行时间难准确预测，长任务还可能饥饿。
- **SRTF**是抢占式 SJF：新任务到达时，比较所有任务剩余时间并运行最短者。短任务响应更好，但抢占更多，也可能让长任务长期得不到运行。
- **RR**让每个任务轮流运行一个时间片，公平且首次响应快。时间片太短会产生大量上下文切换，太长则接近 FCFS。
- **MLFQ**设置多个优先级队列，用历史行为近似预测任务类型：新任务从最高级开始，耗尽累计配额就降级，交互型任务因经常阻塞而保持较高优先级，同级用 RR。

**饥饿**是某任务长期拿不到 CPU。优先级调度可用**老化**缓解：等待越久，逐步提高优先级。MLFQ 常周期性把所有任务提升到最高队列，这既防止低级任务饿死，也让行为已改变的任务重新被评估。

#### 6. 比较管道、消息队列、共享内存、信号、Socket

| IPC      | 核心机制                               | 优点                                               | 局限与适用场景                               |
| -------- | -------------------------------------- | -------------------------------------------------- | -------------------------------------------- |
| 管道     | 内核中的 FIFO 字节流缓冲区             | 简单，天然适合 Shell 流水线                        | 通常单向、无消息边界；匿名管道常用于亲缘进程 |
| 消息队列 | 内核保存一条条有边界的消息             | 消息可暂存，可有类型/优先级                        | 有容量限制和用户态/内核态复制开销            |
| 共享内存 | 多个页表映射同一物理页                 | 建立后少复制，本机大数据量通信快                   | 不自带同步，需锁/信号量并约定布局            |
| 信号     | 内核向进程投递异步事件                 | 适合终止、定时器、子进程退出等通知                 | 信息量小，信号处理函数可安全调用的操作受限   |
| Socket   | 内核套接字端点，支持双向字节流或数据报 | 接口通用，Unix Socket 可本机通信，TCP/UDP 可跨主机 | 协议、序列化、复制和网络栈开销更高           |

选择依据不是简单的“谁最快”，而是数据量、是否跨主机、是否需要消息边界、可靠性、通信拓扑和同步复杂度。大块本机数据常用共享内存加同步；客户端—服务器或跨主机通信通常用 Socket。

#### 7. 用 `counter++` 解释竞态、临界区、互斥和原子性

`counter++` 在机器层面通常分为三步：

```text
load counter → register
register + 1
store register → counter
```

若初值为 50，线程 A 和 B 都先读取 50；A 算得 51 并写回，B 随后也把自己的 51 写回，执行两次自增却只得到 51。这就是结果依赖执行交错的**竞态条件**。

- 访问共享 `counter` 的这段代码是**临界区**。
- 要求同一时刻只有一个线程进入，就是**互斥**。
- 如果自增对其他线程表现为不可分割的整体，就是**原子操作**。

可以用互斥锁包围复合操作，也可以使用语言提供的原子自增。`volatile` 通常只约束某些编译器优化，不能自动把“读—改—写”变成原子操作，也不能完整提供线程间的内存顺序保证。

#### 8. 比较自旋锁、互斥锁、读写锁、信号量、条件变量

| 原语     | 等待方式/语义                       | 适用情况                           | 关键注意点                             |
| -------- | ----------------------------------- | ---------------------------------- | -------------------------------------- |
| 自旋锁   | 拿不到就循环占用 CPU                | 多核、临界区极短、上下文不能睡眠   | 长等待或持锁线程被抢占时浪费 CPU       |
| 互斥锁   | 独占所有权，竞争时通常可睡眠        | 通用临界区保护                     | 通常应由加锁者解锁；避免持锁做慢操作   |
| 读写锁   | 多读者并发，写者独占                | 读多写少且临界区有一定长度         | 维护成本更高，策略不当会饿死读者或写者 |
| 信号量   | 保存 N 个许可，wait 消耗、post 增加 | 资源计数、互斥、事件先后顺序       | 不强调所有权；初值决定语义             |
| 条件变量 | 等待某个由共享状态表达的条件        | “队列非空”“任务完成”等状态等待 | 必须配合互斥锁和 while 重检条件        |

简化判断：保护共享不变量优先考虑互斥锁；允许 N 个并发使用者用计数信号量；等某个状态变真用条件变量；读多写少再评估读写锁；确定等待极短且不能睡眠时才考虑自旋锁。

#### 9. 写出条件变量的 `while + wait` 标准模式

等待者：

```c
pthread_mutex_lock(&mutex);
while (!condition()) {
    pthread_cond_wait(&cond, &mutex);
}
consume_or_use_shared_state();
pthread_mutex_unlock(&mutex);
```

改变条件的一方：

```c
pthread_mutex_lock(&mutex);
change_shared_state();
pthread_cond_signal(&cond);      // 无法确定唤醒谁时可能用 broadcast
pthread_mutex_unlock(&mutex);
```

调用 `wait` 前必须持有 mutex。`wait` 会原子地“释放 mutex 并睡眠”，醒来后重新获取 mutex 才返回，从而避免检查条件与入睡之间丢失通知。

必须用 `while`，因为可能发生虚假唤醒；而且通知只表示状态可能发生变化，被唤醒者重新拿到锁之前，其他线程可能已经消费了资源。条件变量本身不保存业务状态，真正的条件应由受锁保护的共享变量表达。

#### 10. 说出死锁四条件，并给出统一锁顺序的解决方法

死锁的四个必要条件是：

1. **互斥**：资源同一时刻只能由一个执行者使用。
2. **请求并保持**：已经持有资源时继续等待其他资源。
3. **不可剥夺**：资源不能被外部强行收走，只能由持有者释放。
4. **循环等待**：等待关系形成一个环。

例如 A 已持有 L1 等 L2，B 已持有 L2 等 L1，就形成循环等待。

统一锁顺序的方法是给所有锁规定全局次序，如 `L1 < L2 < L3`，所有线程只能从小到大获取、从大到小释放。这样即使线程持有 L1 等 L2，也不会存在另一个线程持有 L2 反过来等 L1，因此等待图无法形成环。

若锁是动态对象，可按稳定 ID、内存地址或显式层级排序，但必须保证排序键在加锁期间稳定。其他工程手段还有缩小临界区、避免持锁等待 I/O、try-lock 失败后释放重试和超时检测。

#### 11. 手算一次 VPN、offset、PFN 到物理地址的转换

假设虚拟地址是 32 位、页面大小是 4 KiB，即 `2^12` 字节：

- 低 12 位是页内偏移 offset。
- 高 20 位是虚拟页号 VPN。

给定虚拟地址 `VA = 0x12345ABC`：

```text
VPN    = VA >> 12          = 0x12345
offset = VA & 0xFFF        = 0xABC
```

查询页表，假设 VPN `0x12345` 映射到 PFN `0x8F012`，则：

```text
PA = (PFN << 12) | offset
   = 0x8F012000 | 0xABC
   = 0x8F012ABC
```

本质上是把虚拟地址中的 VPN 替换成 PFN，页内偏移保持不变。真实系统查页表之前通常先查 TLB，并检查 PTE 的存在位和访问权限。

#### 12. 讲清 TLB 未命中、缺页、非法访问三者区别

三者发生在地址转换的不同层面：

1. **TLB 未命中**：TLB 里没有 VPN 的缓存映射。硬件或内核继续查页表；若 PTE 有效且页面在内存，填充 TLB 后重试即可。它很常见，不是程序错误。
2. **缺页 page fault**：页表表明当前访问需要内核处理。常见情况是合法页尚未载入、匿名页首次分配、COW 写入或栈按需增长。内核能处理时，分配/调入/复制页面并重试；若需要磁盘，代价很高。
3. **非法访问**：地址不属于进程的合法映射，或访问违反读写执行权限。内核无法修复时，Unix 类系统通常向进程发送 `SIGSEGV`/`SIGBUS` 等信号，默认终止进程。

关系可以概括为：

```text
查 TLB 未命中
  → 查页表
     → 页已在内存且权限正确：填 TLB
     → 合法但需建立/调入页面：可恢复的缺页
     → 地址或权限非法：不可恢复，报告进程错误
```

因此“TLB 未命中不等于缺页”，“缺页也不一定是错误”。

#### 13. 说明多级页表、页面置换、Clock、抖动和 COW

- **多级页表**：把虚拟页号分成多段，逐级找到最终 PTE。只为实际使用的虚拟地址区域分配下级表，节省稀疏地址空间的页表内存；代价是 TLB 未命中时要多次访问内存。
- **页面置换**：物理内存没有空闲页框时，内核选择牺牲页。理想 OPT 换出未来最晚使用的页但无法实现；FIFO 简单却可能出现 Belady 异常；LRU 利用局部性但精确维护成本高。
- **Clock/Second Chance**：页面组成环。指针遇到访问位为 1 的页就清零并跳过，遇到 0 的页就换出，是对 LRU 的低成本近似；还可优先换出干净页以避免写回。
- **抖动**：运行进程的活跃工作集总量超过物理内存，刚换出的页很快又要换回，系统大部分时间都在处理缺页和 I/O。可通过减少并发进程、工作集控制、内存限额或增加内存缓解。
- **COW**：多个地址空间先共享只读物理页，某方写入时触发保护异常，再复制出私人页。它让 `fork` 和私有文件映射避免不必要的预先复制。

这几者能串成一条线：多级页表记录映射；访问不在内存的合法页会缺页；内存满时页面置换算法选择牺牲页；选择失误且工作集过大时可能抖动；COW 则通过延迟复制减少不必要的内存占用。

#### 14. 解释 `malloc` 与系统调用、虚拟内存和物理页的关系

`malloc` 通常是 C 运行库的用户态函数，不是每调用一次就进入内核。分配器先管理一批已经取得的虚拟地址区间，通过空闲链表、大小分类、伙伴思想等方式切分和复用小块。

当现有堆空间不足时，分配器才可能通过 `brk/sbrk` 扩展传统堆，或用 `mmap` 获取新的虚拟内存区域。内核建立虚拟地址映射也不代表立即分配并清零全部物理页；现代系统常在程序首次触碰页面时通过缺页异常按需分配物理页。

因此有三个不同层次：

```text
malloc 返回一块可用的用户对象
  → 分配器管理进程的虚拟地址区间
     → 内核页表把已触碰的虚拟页映射到物理页
```

`free` 通常只是把小块归还给用户态分配器，未必立刻归还 OS；只有满足一定条件的大块或空闲区间才可能通过 `munmap` 等方式返还。`malloc` 成功也不保证未来触碰所有页面时一定不会因系统内存不足而失败或被 OOM 处理。

#### 15. 比较 select/poll/epoll，以及 LT/ET

- `select` 每次调用都传入 fd 位图，内核和应用需处理整个集合，返回后还要线性检查，而且通常受 `FD_SETSIZE` 限制。
- `poll` 用 `pollfd` 数组，避免固定的小位图上限，表达更方便，但每次仍传入并扫描全部监视项。
- `epoll` 把“注册兴趣”和“等待就绪”分开。内核长期维护兴趣集合和就绪队列，`epoll_wait` 主要返回已经就绪的 fd，适合大量连接中只有少量活跃的 Linux 服务。

不能机械地说 epoll 永远是 O(1) 或任何场景都最快。所有连接都很活跃时，应用仍要处理大量事件；连接数量较少时，简单的 poll 可能已经足够。

- **LT 水平触发**：只要 fd 仍处于就绪状态就会反复通知，容错性高，默认更容易使用。
- **ET 边缘触发**：主要在状态从未就绪变为就绪时通知，事件更少，但 fd 应设为非阻塞，并在收到事件后循环 `read/accept/write` 直到返回 `EAGAIN`。若只读一部分，缓冲区仍有数据却没有新状态边缘，程序可能再也收不到通知。

它们提供的是**就绪通知**，不是替应用完成业务逻辑，也不等同于完整的异步 I/O。

#### 16. 说明 fd、打开文件表、inode、目录项与硬/软链接

一次典型文件访问关系是：

```text
进程 fd 表中的整数索引
  → 内核打开文件对象（当前偏移、状态标志、引用计数）
     → inode/vnode（权限、所有者、大小、数据块位置等元数据）
        ← 目录项用“文件名 → inode”找到它
```

fd 只是进程内的小整数。`dup` 或 `fork` 后，多个 fd 可以指向同一打开文件对象，因此共享当前偏移；两次独立 `open` 通常有不同打开文件对象和独立偏移，但最终可以指向同一 inode。

- **硬链接**是在另一个目录项中记录同一个 inode 号，所以两个名字地位相同。删除一个名字只减少链接计数；通常不能跨文件系统，也通常禁止普通用户为目录创建硬链接。
- **软链接**是一个保存目标路径的特殊文件，有自己的 inode。它能跨文件系统、能指向目录，但目标被移走后可能悬空。

`unlink` 删除的是目录项。若进程仍打开该文件，内核引用仍存在，数据要等链接数为 0 且最后一个打开引用关闭后才真正释放。

#### 17. 解释 write、页缓存、fsync 与日志文件系统的持久性边界

普通 `write(fd, buf, n)` 成功，通常只表示数据已经从用户缓冲区复制到内核页缓存并被标记为脏，或者至少被内核接受；它不等于数据已经写到掉电不丢的介质。内核稍后才会回写脏页，所以此时断电仍可能丢数据。

`fsync(fd)` 请求把该文件的脏数据和恢复它所必需的元数据推进到稳定存储；`fdatasync` 更侧重数据和影响读取结果的必要元数据。创建新文件、重命名或替换文件时，若还要求“目录项本身”在崩溃后存在，通常还需要对父目录进行同步。`close` 一般不等价于 `fsync`。

日志文件系统主要解决一次文件系统操作要修改多个元数据结构时的**崩溃一致性**。它先把更新意图组成事务写入日志并提交，再更新正式位置；重启后只重放完整提交的事务。日志能避免 inode、位图和目录项处于无法解释的半更新状态，但不自动保证应用层一组独立 `write` 具有数据库事务语义，也不替代应用正确使用 `fsync`。

还要注意设备写缓存和控制器是否正确兑现 flush/FUA 等命令。持久性是一条端到端链路：

```text
用户缓冲区 → 内核页缓存 → 文件系统/日志 → 驱动与设备缓存 → 非易失介质
```

面试中的稳妥结论是：**write 成功表示写入请求被接受；fsync 才用于请求持久化；日志主要保证文件系统结构的一致恢复，三者语义不能混为一谈。**

### 回答开放题的推荐结构

面对“比较 A 和 B”“解释 X”类问题，可按以下顺序回答：

1. **先给定义和结论**：一句话回答问题。
2. **讲核心机制**：数据放在哪里、谁执行、何时切换或唤醒。
3. **比较代价与适用场景**：时间、空间、并发、隔离、可靠性。
4. **给一个具体例子**：最好能描述异常时序。
5. **补边界条件**：避免“永远、一定、完全 O(1)”等绝对化结论。

例如回答“为什么条件变量用 while”：先说醒来不保证条件成立；再解释 wait 原子释放锁、醒后重新竞争锁；接着给出两个消费者争抢一个元素的时序；最后补充虚假唤醒。这比只背“规定如此”更能体现理解。

## 结语：把知识串成一条因果链

操作系统不是互不相关的名词集合：

```text
应用需要运行
  → 进程/线程提供执行抽象
  → 时钟中断让内核收回 CPU，调度器决定谁运行
  → 上下文切换让多个任务共享 CPU
  → 页表与 TLB 让任务安全、高效地共享物理内存
  → 缺页和置换把磁盘扩展成内存的后备
  → 锁、条件变量和信号量约束共享状态的并发访问
  → 系统调用和 IPC 让隔离的进程安全地请求服务与交换信息
  → I/O 栈和文件系统把数据可靠地保存并重新读取
```

面试时真正有价值的不是背出定义，而是能说明：**为什么需要这个机制、它如何工作、解决了什么问题、又引入了什么代价。**
