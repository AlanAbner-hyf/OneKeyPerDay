# 游戏网络同步面试总结

> 面向游戏客户端开发岗位的突击笔记。目标不是背协议名词，而是能围绕一条主线说明： **在延迟、抖动、丢包和带宽限制下，怎样让多台机器看到足够一致、操作足够跟手、且难以作弊的游戏世界。** 全文按约 **30 分钟** 阅读量组织。

## 阅读路线

- **前 20 分钟**：阅读第 1～7 章，掌握同步方案、传输语义、插值、预测与延迟补偿。
- **后 7 分钟**：阅读第 8～9 章，学会从零设计一个同步系统并讨论边界。
- **最后 3 分钟**：遮住第 10 章答案口述，再过一遍第 11 章检查表。
- 时间很紧时，优先阅读标有 **高频** 的章节。

## 1. 先建立整体模型【高频】

### 1.1 为什么游戏不能“把本机画面发给别人”

网络传输有四个基本限制：

- **延迟（latency）**：消息到达需要时间。RTT 是往返时间，单程延迟不能简单保证等于 RTT/2，因为上下行路径可能不对称。
- **抖动（jitter）**：每个包的延迟不同。平均延迟不高，也可能因为到达时间忽快忽慢而卡顿。
- **丢包与乱序**：包可能消失、重复或后发先至。
- **带宽有限**：不能每帧发送完整世界，更不能发送渲染结果。

因此同步的是能重建游戏的**输入、状态或事件**，客户端再在本地渲染。同步系统追求的也不是任意时刻所有内存逐字节一致，而是以下目标之间的平衡：

1. **一致性**：关键玩法结果相同，如谁命中、谁死亡。
2. **响应性**：玩家按键后尽快看到反馈。
3. **平滑性**：其他玩家移动不抖、不瞬移。
4. **公平与安全**：客户端不能自行宣布伤害和奖励。
5. **资源可控**：带宽、CPU、内存能随玩家数量扩展。

这几个目标会冲突。例如，多等 100 ms 再渲染可以吸收抖动、让远端角色更平滑，却增加了观察延迟；完全等待服务器确认可以提高权威性，却让本地操作“粘手”。

### 1.2 三条时间线不要混淆

- **服务器模拟时间**：服务器按固定 tick 推进权威世界。
- **客户端预测时间**：本地玩家通常先于服务器结果，用来保证操作即时反馈。
- **客户端渲染时间**：远端实体通常故意落后服务器一小段时间，以便在两个已知快照间插值。

```text
较旧                                                         较新
远端实体渲染时间 -------- 服务器已确认时间 -------- 本地预测时间
         插值区间                权威状态               未确认输入
```

面试时能讲清这三条时间线，后面的插值、预测和校正就都能串起来。

### 1.3 Tick、帧和发包频率不是一回事

- **逻辑 tick**：模拟世界一次，例如服务器 20 Hz，即每 50 ms 推进一次。
- **渲染帧**：客户端绘制频率，例如 60/120 FPS，可以远高于逻辑 tick。
- **网络发送频率**：可以是 10、20 或 30 Hz，也不必等于逻辑频率。

渲染层在逻辑状态之间插值，所以服务器无需为了 120 FPS 每秒发送 120 份状态。固定步长模拟通常比把逻辑直接绑定可变帧率更容易复现和调试；但固定步长不等于跨平台自然确定性。

## 2. 三类同步方案【高频】

网络模型和底层传输协议是两个维度：状态同步既可基于 UDP，也可基于 TCP；帧同步也不等于“每渲染帧发包”。

| 方案              | 网络主要传什么       | 权威结果如何产生           | 优点                                       | 主要难点                                       | 常见场景                 |
| ----------------- | -------------------- | -------------------------- | ------------------------------------------ | ---------------------------------------------- | ------------------------ |
| 状态同步          | 实体状态、属性和事件 | 通常由服务器模拟           | 容错较好、易做服务端权威、可只同步关注区域 | 带宽较高，要插值、预测和纠错                   | FPS、TPS、MMO、开放世界  |
| 确定性帧同步/锁步 | 每个逻辑帧的玩家输入 | 各端用同样输入自行模拟     | 输入很小，适合大量单位                     | 必须确定性；慢玩家、断线、作弊与中途加入难处理 | RTS、部分回合或竞技游戏  |
| 回滚同步          | 带帧号的输入         | 先预测输入，迟到后回滚重演 | 本地响应快，低延迟下体验好                 | 状态保存、快速重演、副作用处理复杂             | 格斗、体育等少量玩家游戏 |

实践中经常是**混合方案**：移动采用状态同步，本地角色做预测；开火是事件，伤害由服务器判定；部分技能或小玩法使用确定性模拟。

### 2.1 状态同步（snapshot/state replication）

服务器维护权威世界，周期性给客户端发送快照，例如：

```text
tick=1024
player#17: position=(12.3, 5.8), velocity=(2.0, 0), hp=76, anim=Run
```

客户端收到后，不应直接把远端角色瞬移到新坐标，而应缓存快照并插值显示。快照可以是完整状态，也可以只发相对某个已确认基线发生变化的字段。

优点是客户端偶尔算错不会永久扩散，下一份权威状态可以纠正；服务器也容易做反作弊。代价是状态体积大，需要兴趣管理、量化、增量压缩和优先级调度。

### 2.2 确定性帧同步/锁步（deterministic lockstep）

每台机器从相同初始状态开始，对第 `N` 个逻辑帧应用完全相同的一组输入，然后推进相同模拟：

```text
S(N + 1) = Simulate(S(N), Inputs(N))
```

服务器可只收集、排序和广播输入，不必频繁发送全部单位状态。假设 RTS 中 500 个单位都在移动，传“玩家在第 800 帧下令 20 个单位去 A 点”远小于持续发送 500 个坐标。

难点是**确定性**：相同状态和输入必须得到相同结果。常见破坏因素包括：

- 不同 CPU/编译选项造成浮点误差，误差经数千帧放大；
- 无序容器迭代顺序不同，导致碰撞或目标选择顺序不同；
- 随机数种子、调用次数或调用顺序不同；
- 依赖本地时间、线程调度或未初始化内存；
- 不同版本的资源和逻辑代码。

常见手段是定点数或受控浮点、固定更新顺序、确定性随机数、版本校验，并周期性计算世界状态哈希检测不同步。发现不同步后可终止对局，也可从权威快照恢复，取决于架构。

纯锁步若必须等最慢玩家输入，响应会受最慢链路限制。常见做法是加入固定输入延迟：玩家当前输入安排到未来第 `N + k` 帧执行，以缓冲网络抖动。`k` 越大越稳，但手感越慢。

### 2.3 回滚同步（rollback netcode）【难点】

回滚的核心是“**先猜后改**”：尚未收到对手第 101 帧输入时，先预测其继续保持上一次输入并模拟；若真正输入到达后发现猜错，就恢复第 101 帧之前的快照，应用真实输入，再快速重演到当前帧。

例：

```text
已经显示到 104 帧
101 帧：预测对手未出拳
105 帧：收到消息，得知对手在 101 帧按了出拳
处理：恢复 100 帧状态 -> 用真实输入重算 101~105 帧 -> 得到修正后的现在
```

为此需要环形保存最近若干帧的可恢复状态，并保证模拟足够快。音效、粒子、震屏、网络请求等不能在重演时重复触发，通常把它们视为模拟外的**副作用**：延迟到结果确认后播放，或使用事件 ID 去重，或允许可接受的视觉误差。

### 2.4 怎样选择

- 世界大、玩家多、客户端不可信、允许近似视觉一致：倾向**服务器权威的状态同步**。
- 单位极多但玩家数有限、逻辑可以严格确定：倾向**帧同步**。
- 玩家少、每帧输入很小、强调整帧操作和即时响应：考虑**回滚**。
- 不要只说“某方案更好”，要联系玩家数、单位数、输入规模、确定性成本、带宽、反作弊和中途加入来选择。

## 3. 传输协议与消息语义【高频】

### 3.1 TCP 和 UDP 怎么选

**TCP**提供可靠、有序的字节流，并有拥塞控制。适合登录、聊天、商城、配置下载等必须完整到达且不频繁的业务。它没有消息边界，应用层仍需长度字段或其他方式拆包；“粘包/半包”是读取字节流时的正常现象，不是 TCP 出错。

**UDP**提供数据报边界，但默认不保证送达、不保证顺序、不去重，也不替应用完成拥塞控制。它适合位置、朝向等“新状态能覆盖旧状态”的实时数据，并允许游戏按消息类型定制可靠性。

实时移动常不用纯 TCP 的关键原因是**队头阻塞**：较旧字节丢失时，后续已到达数据也不能越过它交给应用。但这不意味着 UDP 必然更快；如果在 UDP 上把所有消息也做成一个严格有序、无限重传的队列，同样会重新制造队头阻塞。

### 3.2 先定义消息语义，再谈协议

| 消息                    | 典型语义                                   | 理由                                                 |
| ----------------------- | ------------------------------------------ | ---------------------------------------------------- |
| 高频位置/朝向           | 不可靠、有序取最新（unreliable sequenced） | 旧位置到得再晚也没有价值                             |
| 玩家输入                | 常带序号，冗余发送或可靠传输               | 少一个输入可能影响模拟；新输入不一定能完全覆盖旧输入 |
| 生成/销毁实体、背包变化 | 可靠                                       | 丢失会造成长期逻辑错误                               |
| 聊天                    | 可靠、有序                                 | 内容必须完整且顺序有意义                             |
| 独立音效/特效提示       | 视玩法可不可靠                             | 偶尔丢失通常优于迟到很久                             |

可靠性和有序性应拆开设计。不同消息最好放在独立逻辑通道，避免“背包消息丢包”阻塞“角色移动”。

### 3.3 在 UDP 上做有限可靠传输

常见包头字段：

```text
connection_id | sequence | ack | ack_bits | server_tick | payload
```

- `sequence`：本包递增序号，用于去重、识别乱序和估计丢包。
- `ack`：当前收到的最新对端序号。
- `ack_bits`：一个位图，表示 `ack` 之前若干个包是否收到，可一次确认多个包。
- 可靠消息未被确认时按重传策略再次发送；不可靠旧消息则直接淘汰。

重传超时不能写死成一个很小常数，否则网络一抖就产生重复包和拥塞。可根据平滑 RTT 及其波动估计 RTO，并限制重传次数和在途数据。生产系统还必须有速率限制或拥塞控制：丢包时继续无上限加大发送只会让延迟越来越高，形成“延迟尖峰”。

序号会回绕，例如 16 位序号从 65535 回到 0，比较新旧不能直接使用普通整数大小关系，要在模空间内比较。

### 3.4 包大小、分片与序列化

- IP 分片中任意一片丢失，整个数据报就无法重组；实时 UDP 包通常控制在路径 MTU 之下。不能把 1500 字节当作所有链路都安全的应用载荷，还要扣除 IP/UDP 和可能的隧道开销。
- 大消息在应用层分片时要带消息 ID、分片索引、总片数、长度和超时，并严格限制上限，防止恶意包耗尽内存。
- 明确整数宽度、字节序、协议版本和可选字段，不能直接把含 padding、指针或平台相关布局的 C++ 结构体 `memcpy` 到网络。
- 对坐标、角度、单位向量等量化。例如地图坐标范围已知时，用 16 位整数映射坐标，精度足够且比 32 位浮点省带宽。
- 对输入和长度做边界校验；解析网络包时默认对方不可信。

## 4. 远端角色如何显示得平滑【高频】

### 4.1 快照插值（snapshot interpolation）

客户端维护按服务器时间排序的快照缓冲区，把渲染时刻设为：

```text
render_time = estimated_server_time - interpolation_delay
```

若渲染时刻位于快照 A、B 之间，位置可线性插值：

```text
alpha = (render_time - A.time) / (B.time - A.time)
position = A.position * (1 - alpha) + B.position * alpha
```

例：服务器每 50 ms 发一次快照。客户端故意落后 100 ms 渲染，那么即使某个包晚到几十毫秒，通常仍能在缓存中找到渲染时刻两侧的 A 和 B，角色就不会每 50 ms 跳一次。代价是看到的远端世界额外旧了约 100 ms。

旋转通常使用适合旋转表示的插值，如四元数的 slerp/nlerp，而不是随意逐分量线性插值。动画状态等离散值也不能直接 lerp，需要按状态机或事件处理。

缓冲太短会频繁耗尽、被迫外推；太长则延迟明显。可以根据抖动动态调整，但要避免延迟不断来回变化造成视觉速度忽快忽慢。

### 4.2 外推与航位推算（extrapolation/dead reckoning）

缓存没有更新快照时，可短时间按速度预测：

```text
predicted_position = last_position + velocity * dt
```

它适合短暂丢包和惯性明显的对象，但角色突然转向、撞墙或急停时会猜错。因此一般限制最大外推时长；新权威状态到达后，将小误差在数帧内平滑消除，大误差直接拉回。

**例子：** 汽车在直道上丢 100 ms 包，用速度外推往往自然；角色在墙角蛇形走位时外推容易穿墙。预测模型越了解加速度、碰撞和控制输入，结果越准，但实现和作弊面也更复杂。

### 4.3 本地预测与服务器校正（client prediction & reconciliation）【难点】

如果玩家按 W 后必须等待一次网络往返才移动，50 ms RTT 也能明显感觉迟钝。因此客户端立即用本地输入模拟自己，同时把每个输入带序号发送给服务器，并保留尚未确认的输入。

服务器返回权威状态时，同时告知“已经处理到输入 42”。客户端：

1. 把本地状态恢复为服务器确认的状态；
2. 丢弃 `<= 42` 的已确认输入；
3. 按原顺序重放 43 之后的未确认输入；
4. 将得到的逻辑位置立即作为正确状态，视觉表现可对小误差平滑追赶。

```text
本地已预测输入：40 41 42 43 44
服务器返回：状态 P，并确认已处理到 42
客户端：从 P 重新执行 43、44，得到新的预测位置
```

这叫**服务器和解/重校正**。要尽量让客户端与服务器共享移动规则、碰撞数据和 tick 步长，否则会持续校正。客户端预测只改善“自己的操作反馈”，不能凭空消除网络延迟，也不能让客户端成为权威。

常见视觉策略：误差小则让渲染节点逐渐靠近逻辑节点；误差超过阈值或涉及穿墙、坠落等关键错误则立即纠正。只做平滑但不修正逻辑状态，会让碰撞和画面长期分离。

### 4.4 时间同步

客户端需要估计服务器时间，不能假设本地系统时钟与服务器完全一致。可周期性交换时间戳，用多次样本估计 RTT、时钟偏移并平滑更新，尽量排除高延迟异常样本。

玩法消息最好使用服务器 tick 或单调时钟，不依赖可能被系统校时向前/向后跳变的墙上时钟。时间同步只能估计，单凭一次 RTT 无法精确知道上下行各用了多久。

## 5. 射击判定与延迟补偿【高频难点】

### 5.1 为什么“我明明打中了”

射手屏幕显示的是稍旧的远端角色。射手点击时，目标在服务器当前时刻可能已经走开：

```text
射手看到的目标位置（历史） ---- 网络传输 ---- 服务器当前目标位置
             开枪                                   已移动
```

若服务器只拿当前位置判定，低延迟玩家体验相对更好，高延迟玩家会频繁出现准星命中但服务器判空。

### 5.2 服务器回溯（lag compensation / server rewind）

服务器保存最近一小段时间的碰撞体历史。收到开火请求后：

1. 根据输入的服务器 tick/时间估计射手开枪时刻；
2. 将参与判定的目标碰撞体回溯到该历史时刻；
3. 做射线或命中检测；
4. 恢复当前状态，由服务器决定伤害。

这会产生经典现象：被击中者已经躲到掩体后，仍可能因对方看到的历史画面而中弹。它不是免费消除延迟，而是在“射手所见即所得”和“被击者当前已经躲开”之间选择公平策略。

服务器必须限制最大回溯窗口，验证射速、弹药、起点、视角变化和时间戳范围，不能相信客户端自报的“我在两秒前击中了”。高延迟也不应带来无限优势。

### 5.3 命中扫描与实体弹丸

- **命中扫描（hitscan）**：开火瞬间做射线判定，通常适合服务器回溯。
- **实体弹丸**：有飞行时间，可由服务器模拟权威轨迹，客户端先生成纯视觉弹丸；之后根据服务器结果校正。
- 客户端可以立即播放枪口火焰、后坐力和开枪音效来保证响应性，但伤害、死亡和奖励应由服务器确认。

## 6. 服务器怎样把世界发给每个客户端

### 6.1 服务端权威与网络所有权

**服务器权威**不是所有东西都必须等服务器后才显示，而是最终玩法状态由服务器裁决。客户端可以预测移动和表现特效，但不能自行决定位置、伤害、掉落、货币等关键结果。

有些对象可把模拟所有权临时交给某客户端以降低成本或改善手感，但服务器仍需验证结果，并考虑所有者断线、切换所有者和恶意数据。竞技游戏对关键对象通常更保守。

### 6.2 兴趣管理/AOI【高频】

服务器不应把所有实体发给所有玩家，而应维护每个连接的关注集合（Area of Interest）：

- 按距离、视野、房间、队伍或玩法相关性筛选；
- 空间划分可用网格、四叉树、八叉树等；
- 进入 AOI 时发送生成及必要完整状态，离开时发送销毁/休眠通知；
- AOI 边界最好带迟滞，避免实体在边缘来回抖动导致反复生成销毁。

**量级例子：** 100 个实体每个快照 40 字节、每秒 20 次，仅载荷就是 `100 × 40 × 20 = 80 KB/s`，还没算包头和重传。若 AOI 平均只保留 20 个实体，理论载荷可降到约 16 KB/s。

### 6.3 增量同步、基线和优先级

- **脏标记**：只发发生变化的字段。
- **增量/差分快照**：发送当前状态相对某份已知基线的变化。基线必须是客户端已确认拥有的版本，不能想当然地以上一个“已发送”快照为基线，因为它可能丢失。
- **量化与位打包**：用业务允许的精度换带宽。
- **优先级调度**：带宽预算不够时，优先附近敌人、正在交互的对象和累积很久未更新的实体；远处装饰物降低频率。
- **周期完整刷新或可恢复关键帧**：避免一次增量丢失造成永久错误。具体选择取决于可靠通道和基线设计。

不要只按距离排序。一个远处正在瞄准玩家的敌人，可能比脚边静止的箱子更重要。常见优先级会综合距离、屏幕可见性、玩法重要度、变化幅度和“自上次发送以来的时间”。

### 6.4 生命周期和事件

实体同步至少要处理：唯一网络 ID、生成、属性初始化、更新、休眠/离开 AOI、销毁和 ID 复用。乱序时可能先收到更新后收到生成，或销毁后又到达旧更新，因此消息要带版本/代数或 tick，并定义缓存或丢弃规则。

事件与状态要区分：

- “门当前是开着的”是**状态**，新客户端加入后仍需知道；
- “门刚才发出吱呀声”是**瞬时事件**，迟到太久就没有播放价值。

只同步事件会让中途加入者缺少当前世界；只同步状态又可能重复或漏掉一次性表现。

## 7. 把一场移动和开火串起来【综合例子】

以服务器权威 FPS 为例：

1. 客户端 A 在逻辑 tick 300 采集移动和开火输入，输入带序号；本地立即预测移动，并播放开枪表现。
2. 输入通过 UDP 发送。关键输入可在后续多个包中冗余携带，直到服务器确认。
3. 服务器验证移动速度、射速和弹药，按规则模拟 A；对开火使用受限的历史回溯判定是否击中 B。
4. 服务器推进权威 tick，按 A、B 各自的 AOI 和带宽预算生成快照；快照带服务器 tick 和已处理输入序号。
5. A 收到快照后，以权威状态为起点重放未确认输入，修正自己的预测误差。
6. A、B 对其他远端角色都在快照缓冲区中插值显示；短暂断流时有限外推，恢复后按误差大小平滑或瞬移纠正。
7. 伤害和死亡只认服务器结果；客户端预测的枪口表现与服务器确认的命中效果分层处理。

这套流程同时使用了：输入序号、客户端预测、服务器权威、服务器和解、快照插值、AOI、延迟补偿和不同可靠性通道。面试开放题可沿这条链回答。

## 8. 常见故障、反作弊与工程化

### 8.1 高频故障定位

| 现象               | 可能原因                             | 排查方向                             |
| ------------------ | ------------------------------------ | ------------------------------------ |
| 远端角色周期性顿挫 | 快照频率低、缓冲过短、抖动           | 观察到包间隔、插值缓冲耗尽率         |
| 本地角色频繁拉回   | 客户端/服务器移动逻辑不一致          | 输入序号、tick、碰撞数据、浮点与步长 |
| 延迟越来越高       | 发送超过链路能力、重传风暴、队列膨胀 | 在途数据、丢包、RTT、发送队列长度    |
| 偶发实体复活       | 生成/销毁乱序或 ID 复用              | 实体代数、消息 tick、去重逻辑        |
| 增量状态永久错误   | 使用了客户端未收到的基线             | 基线确认、关键帧、丢包恢复           |
| 偶发“双重伤害”   | 可靠事件重传但接收端未去重           | 事件唯一 ID 与幂等处理               |

### 8.2 网络条件模拟

不能只在本机低延迟环境测试。至少覆盖：

- 固定延迟和上下行不对称延迟；
- 抖动、随机丢包、突发丢包、乱序和重复包；
- 限带宽与队列膨胀；
- 断线、重连、服务器迁移或切场景；
- 不同帧率、CPU 卡顿和后台切换。

记录包序号、消息类型、字节数、客户端/服务器 tick、RTT、丢包率、插值缓冲、预测误差和校正次数。网络问题若没有时间线日志和指标，通常只能靠猜。

### 8.3 安全边界

- 客户端发送“我按了什么/想做什么”，服务器验证后决定“发生了什么”。
- 验证速度、加速度、冷却、资源消耗、视线、距离和时间戳；对异常频率限流。
- 不要把不在 AOI 内的隐藏敌人信息发送给客户端，否则即使不渲染也可能被外挂读取。
- 加密与身份认证能防窃听、篡改和伪造连接，但不能让已被玩家控制的客户端变可信。
- 协议解析要防越界、整数溢出、压缩炸弹和无限分片缓存。

### 8.4 断线重连与中途加入

帧同步的新客户端不能只拿到未来输入，必须得到某个完整状态检查点，再补齐检查点之后的输入。状态同步通常发送当前 AOI 的完整基线，再开始增量流。恢复过程要有版本号和明确切换点，避免旧连接的迟到包污染新会话。

## 9. 面试设计题的回答模板

遇到“设计一套某游戏的网络同步”时，可按以下顺序回答：

1. **澄清需求**：游戏类型、玩家数、单位数、是否强竞技、可接受延迟、目标平台和弱网环境。
2. **确定权威模型**：服务器权威还是点对点；哪些结果绝不能信客户端。
3. **选择同步模型**：状态、帧、回滚或混合，并说明为什么适合对象规模与玩法。
4. **划分消息语义**：哪些可靠/不可靠、是否有序、能否被新状态覆盖、是否需要去重。
5. **设计时间轴**：服务器 tick、输入序号、时间同步、客户端渲染延迟。
6. **处理体验**：本地预测与和解、远端插值、有限外推、射击延迟补偿。
7. **控制资源**：AOI、优先级、发送频率、量化、增量基线、带宽预算。
8. **覆盖异常与安全**：丢包乱序、断线重连、校验、限流、反作弊。
9. **说明验证方式**：弱网模拟、回放复现、指标和压力测试。

一个优秀回答不只是报出技术名词，还会主动讲**代价和边界**。例如：“我会给远端角色保留约两个到三个快照间隔的插值缓冲；它提高平滑度但增加观察延迟，实际值根据发送频率和抖动分位数动态调整。”

## 10. 高频面试速答

### 10.1 状态同步和帧同步有什么区别？

状态同步传结果，通常由服务器模拟并下发权威快照，容错与反作弊较好，但更占带宽；帧同步传输入，各端确定性模拟，输入带宽低且适合大量单位，但对确定性、慢客户端、断线恢复和作弊控制要求高。实际项目常混合使用。

### 10.2 为什么实时游戏常用 UDP？

因为很多实时状态过期后重传已无意义，UDP 允许应用按消息定制是否可靠、是否有序，并避免一个旧包阻塞所有新消息。但 UDP 不自带可靠性、拥塞控制和安全能力，这些必须由应用或成熟传输层补齐；登录和交易等仍可使用可靠流。

### 10.3 UDP 如何保证可靠？

用连接 ID、序号、ACK/ACK 位图、去重、超时重传、滑动窗口和拥塞/速率控制；同时按逻辑通道隔离顺序。只对真正需要的消息可靠化，位置等过期状态保留最新即可。

### 10.4 插值、外推和预测有什么区别？

插值在两个已知历史状态之间计算，稳定但增加延迟；外推从最后状态向未知未来推算，没额外等待但可能猜错；客户端预测特指用本地输入提前模拟自己的角色，随后用服务器确认状态重放未确认输入并校正。

### 10.5 客户端预测为什么还会拉回？

因为客户端看到的信息不完整，且移动规则、碰撞顺序、时间步长或状态可能与服务器不同。服务器是权威，差异必须纠正。工程上要减少两端模拟差异，小误差平滑，大误差立即修复，并统计校正频率定位问题。

### 10.6 帧同步怎样保证一致？

相同初态、相同版本、相同帧输入和顺序、确定性数学与随机数、固定更新次序，并定期对关键状态算哈希。浮点、无序容器、线程调度、本地时间和未初始化数据都是风险。哈希只能发现不同步，恢复还需要权威快照或其他策略。

### 10.7 什么是服务器权威？还需要客户端预测吗？

服务器权威表示最终玩法结果由服务器裁决，不表示客户端所有表现都要等待服务器。客户端仍可预测移动、枪口火焰等以改善响应，收到服务器结果后再和解；伤害、奖励等关键状态不能由客户端决定。

### 10.8 为什么快照差分必须基于“已确认”基线？

如果服务器以刚发出但已经丢失的快照 A 为基线，只发“相对 A 的变化 B”，客户端缺少 A 就无法重建 B。应基于客户端确认收到的基线，或提供独立可恢复的关键帧机制。

### 10.9 怎样降低带宽？

先做 AOI 和优先级，避免发送无关对象；再降低不重要对象频率、只发脏字段、基于已确认状态做增量、量化并位打包。优化前要按消息类型测量，不能只依靠通用压缩，因为小包压缩头和 CPU 成本可能得不偿失。

### 10.10 高延迟玩家开枪怎样判定？

服务器保存有限历史，根据经过验证的开火时刻回溯目标碰撞体后判定，再由服务器应用伤害。它改善射手的所见即所得，但会让被击者产生“躲到墙后仍中弹”的感受，因此要限制回溯窗口并平衡双方公平性。

### 10.11 如何处理丢包后的角色移动？

远端角色可在插值缓冲内继续播放；缓冲耗尽后只做有限外推，超过时长则减速或冻结。新状态到达后按误差大小平滑或立即纠正。不能无限外推，否则角色会穿墙或偏离很远。

### 10.12 如何定位偶发不同步？

为输入和状态记录 tick、序号与哈希，保留可重放日志；在相同版本上离线重演，二分查找首个哈希不同的 tick，再比较该帧的输入、实体更新顺序、随机数调用和关键状态。仅看最终错误画面很难找到最早原因。

## 结语：记住一条因果链

```text
网络不可靠且有延迟
  -> 选择状态/输入以及可靠性语义
  -> 用 tick、序号和确认建立顺序与时间
  -> 本地预测保证响应，服务器权威保证正确
  -> 插值吸收抖动，有限外推应对短暂断流
  -> AOI、优先级、增量和量化控制带宽
  -> 用校验、回放、弱网模拟和指标验证系统
```

面试中先给结论，再讲机制，用一个具体时间线举例，最后补上代价与边界。能把这条链讲完整，比孤立地背“UDP、帧同步、插值”更有说服力。
