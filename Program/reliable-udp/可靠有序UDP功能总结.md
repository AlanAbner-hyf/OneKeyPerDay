# 可靠有序 UDP 功能总结

整理日期：2026 年 10 月 17 日。

## What：在 UDP 上实现消息级可靠有序传输

本项目从 Windows 客户端与 Linux 公网服务器之间的 UDP Echo 开始，逐步加入 Message ID、ACK、超时重传、去重、乱序缓存和会话管理。

代码位于 [Program/reliable-udp](../../Program/reliable-udp/README.md)。编译、运行、协议格式和默认参数见项目 README。本总结侧重实现思路，以及每个功能解决的问题。

## Why：理解可靠有序需要哪些机制配合

UDP 提供数据报收发，但不会替应用保证可靠到达、有序交付、重复消除或自动重传。游戏中的某些操作具有顺序关系，例如先生成玩家，再装备武器，随后开始比赛。

这个实验的目标是把这些能力逐项实现出来，观察它们之间的依赖：

```text
消息身份 → 确认与重传 → 去重 → 有序缓存与交付
                              ↓
                      会话隔离与资源生命周期
```

可靠性不只是“多发送几次”。接收端需要识别重复消息，发送端需要识别迟到确认，有序接收需要保存缺口之后的数据，而所有这些状态都需要有明确的归属、容量和结束条件。

## Content：已实现功能与关键设计

### 1. 原始 UDP Echo

最初的通信链路是：

```text
Windows 客户端
    → 向 Linux 公网 IP 的 UDP 9000 发送文本
Linux 服务端
    → 接收数据及来源 IP:Port
    → 向来源地址原样回复
Windows 客户端
    → 接收并核对回复
```

这一阶段验证了网络地址、端口、socket 收发和公网返回路径。一次 Echo 成功只代表这一次往返成功，不代表 UDP 已经可靠。

随后，客户端加入交互输入：读取完整一行，按回车后发送，再等待下一条输入。当前普通模式仍采用停等方式，一条消息确认后才处理下一条。

### 2. 模拟 ACK 丢失

服务端故意跳过部分回复，使丢包实验能够重复出现。

当前版本每处理第 3 个已接纳的 DATA 数据报，就跳过它的 ACK。重复 DATA 也参加计数，控制消息和错误回复不参加；计数在整个服务端范围内共享。

处理顺序是：

```text
收到 DATA
    → 校验会话和消息
    → 交付、缓存或识别重复
    → 决定是否模拟丢弃 ACK
```

这模拟的是“请求已被接纳，但回复没有回到客户端”，正好可以验证重传是否导致重复业务。它不等于随机丢包，也不直接制造请求乱序。

### 3. Message ID 区分业务消息

每个会话的业务消息从 ID=1 开始连续编号。

| 情况                         | ID 的处理                         |
| ---------------------------- | --------------------------------- |
| 用户提交一条通过校验的新输入 | 分配新 ID                         |
| 同一条消息超时重传           | 保持原 ID                         |
| 用户再次输入相同文本         | 分配另一个 ID，视为另一条业务消息 |
| 输入过长被拒绝               | 不占用 ID，避免留下永久缺口       |
| ID 达到 uint32_t 最大值      | 结束会话，不允许回绕后复用        |

因此，去重依据是消息身份，不是正文内容。

在会话引入之后，完整的消息身份是：

```text
Session ID + Message ID
```

服务器还会检查数据报来源是否与创建会话时的来源地址一致。

### 4. 安全解析消息

两端各自在自己的源文件中保留 parse_message()，解析消息的 ID 与正文部分。外层的消息类型、Session ID 等字段由调用逻辑处理。

解析规则包括：

- 始终使用 recvfrom() 返回的实际字节数，不假设数据以空字符结尾。
- 在有效范围内寻找第一个分隔冒号。
- ID 不得为空，只接受十进制数字。
- 在乘 10、加数字之前检查 uint32_t 溢出。
- 正文可以为空，可以包含空格、冒号和空字节。
- 只有完整解析成功后才写入输出参数。

解析器本身允许整数 0；服务端接纳业务 DATA 时额外拒绝 ID=0。

早期曾出现“客户端发送十进制文本 ID，服务端按 4 字节二进制整数读取”的问题。当前两端使用相同的文本协议，不再对文本 ID 使用 ntohl()。

### 5. ACK、超时重传与固定截止时间

当前 ACK 直接确认某个会话内的 Message ID，不再通过正文回显判断确认结果。

发送一条业务消息时：

```text
最多尝试 3 次
    → 发送相同 Session ID、Message ID 和正文
    → 记录本轮截止时间：现在 + 5 秒
    → 在截止时间之前接收回复
         匹配的 ACK：确认成功
         旧会话、旧 ID 或无效 ACK：忽略并继续等待
         当前会话的 ERROR：终止
         超时：进行下一次发送
```

计时使用 steady_clock，避免系统墙上时间调整影响超时判断。每次接收只等待本轮剩余时间，旧回复不会让等待重新从 5 秒开始。

这里有两个不同的循环：外层控制发送次数，内层处理本轮收到的多个数据报。无效回复只影响内层，不能消耗外层的重传次数。

重试耗尽后，客户端不继续读取并发送后续消息，而是结束会话。因为缺少一个 ID 后，后续消息可能一直无法交付。

“未确认”不能解释为“服务端没执行”：服务端可能已经处理，只是所有 ACK 都丢失。因此程序不会自动建立新会话并再次发送同一业务操作。

### 6. 去重与乱序缓存

服务端的 Session 状态主要包括：

| 字段          | 作用                                       |
| ------------- | ------------------------------------------ |
| endpoint      | 建立会话时的客户端来源 IP:Port             |
| client_nonce  | 识别同一次握手请求的重试                   |
| next_id       | 下一条允许交给业务的 Message ID            |
| pending       | 已接纳但尚不能交付的 ID → 正文缓存        |
| pending_bytes | 缓存正文占用的总字节数                     |
| last_activity | 最近一次被认可的会话活动时间               |
| gap_since     | 当前缺口开始，或最近一次有序交付推进的时间 |

对于合法的业务 ID：

| ID 与 next_id 的关系 | 处理                                       |
| -------------------- | ------------------------------------------ |
| 小于                 | 已交付过，只回复 ACK，不再次执行业务       |
| 等于                 | 立即交付，推进 next_id，并尝试连续交付缓存 |
| 大于                 | 检查重复及容量，接纳后缓存并 ACK，暂不交付 |

对于已经缓存的同一 ID：

- 正文相同：认定为重传，不重复插入，仍然可以 ACK。
- 正文不同：认定为身份冲突，使会话失效，返回 ID_CONFLICT，不发送成功确认。

已经交付的历史消息只依据 ID 去重，不永久保存正文逐条比较。因此发送端必须遵守“同一消息身份始终对应相同正文”的约定。

重复消息也需要确认，因为发送端可能只是没有收到上一次 ACK。

### 7. 按序交付及缓存清理

以到达顺序 3、1、2、2 为例：

| 收到的消息 | 交付动作                   | 交付后等待的 ID | 剩余缓存 |
| ---------- | -------------------------- | --------------- | -------- |
| M3         | 暂不交付                   | 1               | M3       |
| M1         | 交付 M1                    | 2               | M3       |
| M2         | 交付 M2，再交付缓存中的 M3 | 4               | 空       |
| 重复 M2    | 不再次交付                 | 4               | 空       |

交付缓存时，先取出正文交给业务，再删除缓存条目、扣除缓存字节数、推进 next_id。

所有交付都经过 deliver()，目前这个函数只打印 ID 和正文。日志中的 [Deliver] 才代表实验中的业务交付；ACK 或 [Buffered] 都不能替代它。

next_id 使用 uint64_t 保存，业务 ID 仍是 uint32_t。交付最大业务 ID 后，接收进度不会回绕到 0。

### 8. 显式会话建立与隔离

仅以 IP:Port 作为消息状态的身份不足以区分客户端重启，因为地址可能被复用，新进程的 Message ID 又会从 1 开始。

现在采用显式握手：

```text
客户端生成 nonce=N
    → HELLO:N
服务端创建 Session ID=S，并保存来源地址、nonce 和接收状态
    → WELCOME:N:S
客户端验证来源、nonce 和 Session ID 格式
    → 保存 S，之后所有业务消息携带 S
```

N、S 在这里是示意，实际是 32 个小写十六进制字符。

nonce 标识一次建立请求，由客户端生成；Session ID 标识会话，由服务端生成。二者不要混为一谈。

同一来源和 nonce 的 HELLO 重试，如果对应会话仍有效，就得到原来的 Session ID，且不会重置交付进度。旧会话消失后，即使迟到的 HELLO 创建了新状态，也会获得新的 Session ID；携带旧 Session ID 的 DATA 仍然不能复活旧状态。

服务器只允许 HELLO 创建会话，DATA 永远不能隐式创建会话。未知、已关闭、过期或来源不匹配的 Session ID 会被拒绝。

随机 Session ID 用于区分状态，并未实现身份认证或加密。

### 9. 会话结束、过期和缓存上限

当前有三类结束方式：

| 情况                                           | 行为                               |
| ---------------------------------------------- | ---------------------------------- |
| 用户输入 /quit、输入结束或已建立会话后发送失败 | 客户端尝试发送一次 CLOSE，然后退出 |
| 空闲达到 60 秒                                 | 服务端删除整个会话                 |
| 存在乱序缓存，缺口连续 30 秒没有推进           | 服务端使会话失效并清理缓存         |

CLOSE 是尽力通知，没有确认与重传机制。Ctrl+C 或断网可能让它无法发送，服务端依靠超时清理兜底。服务器接收等待每秒唤醒，即使没有新数据报，也能检查过期状态。

重复 DATA 可以更新活动时间，但不会重置缺口等待时间。重复 HELLO 也不刷新已有会话寿命，防止重复请求重置状态。

资源限制包括：

- 最多同时保留 128 个会话。
- 一个会话最多缓存 64 条乱序消息。
- 缓存正文总量最多 256 KiB，容器额外开销不计入该字节值。
- 未来消息的 ID 与 next_id 之差最多为 64。

接纳不了的新消息返回 RECEIVE_LIMIT，不发 ACK，也不挤掉已经接纳的缓存。当前客户端收到错误后会结束会话。

这里选择的是“资源不足时明确失败”，还不是带发送速率调节或窗口协商的流量控制。

### 10. 可靠性、有序性和业务成功的区别

可靠有序不是对所有网络故障都保证成功。当前保证具有会话边界：

1. 有效会话内，按消息身份去重，按连续 ID 交付。
2. 丢包可以通过有限次重试恢复。
3. 不能恢复时终止会话，不自动跳过缺口。
4. 服务端关闭、重启或会话失效后，不承诺恢复未交付消息。
5. ACK 只表示消息已被接纳，可能仍在乱序缓存中。
6. 若需要确认扣款、装备武器等业务执行成功，需要另行设计业务结果回复与必要的持久化。

例如 M3 已得到 ACK，但 M1、M2 一直不到，最终会话缺口超时，M3 会随会话被清理。它没有被交给业务，也不能因为曾收到 ACK 就判断它已经执行。

关闭会话的设计目前是中止和清理，不是“保证所有待交付消息处理完毕”的优雅关闭。

### 11. 与最初 Gaffer 方案的关系

最初讨论的方案区分 Packet 与 Message，通过 Packet ACK 和映射关系确认消息；当前实现采用更直接的学习路线。

| 方面                 | 当前项目                 | 最初讨论的后续目标                 |
| -------------------- | ------------------------ | ---------------------------------- |
| 业务可靠身份         | Session ID + Message ID  | Message ID 或通道内消息编号        |
| 确认方式             | 直接对 Message ID 发 ACK | Packet ACK 映射到包内消息          |
| 一个数据报的业务内容 | 一条消息                 | 可合并多条消息                     |
| Packet Sequence      | 未实现                   | 独立维护                           |
| ack / ack_bits       | 未实现                   | 批量、冗余确认 Packet              |
| 发送方式             | 普通模式逐条停等         | 可同时维护多条未确认消息并进行调度 |
| 重传方式             | 当前消息超时后重新发送   | 未确认消息可放入后续新 Packet      |

因此，目前已经理解并实现了消息层的核心机制，但不能把现有代码称为完整的 Gaffer 可靠 UDP 实现。

### 12. 验证方式与范围

当前客户端内置 --test-order，构造 3、1、2、2 的发送序列。它用于检查服务器的乱序缓存、连续交付和去重，不模拟网络自然产生的随机乱序。

tests/test_sessions.py 覆盖会话隔离、重复握手、旧包拒绝、资源限制、过期、身份冲突、重传失败停止，以及迟到和无效 ACK 的过滤。它还使用真实 Windows 客户端与服务端会话逻辑进行本地 UDP 联调。

测试中的服务端使用 Windows 适配收发循环，Linux 主循环仍需在 Linux 上编译运行。自动化测试不能替代公网安全组、防火墙和实际链路验证。

后续可以继续补充请求方向丢包、随机延迟与乱序、长时间运行和真实网络断开恢复实验。

### 13. 当前尚未实现的能力

- 多条业务消息同时等待确认的发送窗口。
- 根据 RTT 调整重传超时、快速重传、发送节奏和拥塞控制。
- Packet ACK 位图与多消息合包。
- 服务端主动发送业务消息的可靠有序通道。
- 多个独立有序通道，以及可靠、非可靠消息的组合调度。
- 应用层分片、重组和路径 MTU 处理。
- 心跳、地址迁移、跨进程重启恢复和持久化。
- 认证、加密和完整的公网攻击防护。
- 独立于传输 ACK 的业务执行结果确认。

当前实现适合作为学习原型：功能链条已经贯通，下一阶段可以先扩大失败场景验证，再从停等发送演进为允许多条消息在途的发送窗口。
