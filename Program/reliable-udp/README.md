# Reliable Ordered UDP

一个用于学习可靠有序消息传输的 C++17 项目：Windows 客户端通过公网 IPv4 与 Linux 服务端通信，在 UDP 上实现消息编号、超时重传、去重、乱序缓存和会话管理。

当前范围是**客户端到服务端、单个有效会话内的可靠有序消息**。发生无法恢复的失败时终止会话，不跳过缺失消息继续交付。服务端的业务处理入口目前是打印日志。

- 客户端：[client.cpp](client.cpp)
- 服务端：[server.cpp](server.cpp)

## 已实现的功能

| 功能          | 当前行为                                                              |
| ------------- | --------------------------------------------------------------------- |
| 公网 UDP 通信 | Windows Winsock 客户端与 Linux socket 服务端通信，使用 IPv4、UDP 9000 |
| 交互式输入    | 每行输入生成一条消息，支持空正文、空格和正文中的冒号                  |
| Message ID    | 会话内从 1 连续分配，重传沿用原 ID                                    |
| ACK 与重传    | 逐条确认消息；每次最多等待 5 秒，总共最多发送 3 次                    |
| 迟到回复处理  | 忽略旧 ID、旧会话和无效 ACK，不重置当前等待期限                       |
| 消息去重      | 已交付消息不再次执行业务；已缓存的相同消息不重复保存                  |
| 有序交付      | 乱序消息先缓存；缺口补齐后，连续交付并移除缓存                        |
| 会话隔离      | HELLO 握手后由服务端分配 Session ID，新会话不继承旧交付进度           |
| 资源限制      | 限制会话数量、提前到达的 ID 范围、缓存条数和正文总字节数              |
| 失败与清理    | 关闭、空闲超时、缺口停滞或身份冲突时清理会话                          |
| 实验支持      | 每第 3 个已接纳 DATA 的 ACK 被模拟丢弃；支持固定乱序序列测试          |

现在是一条业务消息对应一个 DATA 数据报，ACK 直接确认 Message ID。尚未实现独立 Packet Sequence、ack_bits、Packet 到 Message 的映射或多消息合包。

## 文件说明

| 文件       | 用途                                                     |
| ---------- | -------------------------------------------------------- |
| client.cpp | 当前客户端，包含交互模式和 --test-order 模式             |
| server.cpp | 当前 Linux 服务端，包含会话状态、有序接收和 UDP 收发循环 |

两端各自在自己的源文件中定义 parse_message()，不依赖公共协议头文件。

## 环境要求

- Linux 服务器：支持 C++17 的 g++，可被客户端访问的公网 IPv4。
- Windows 客户端：支持 C++17 的 MinGW-w64 g++，运行于 PowerShell。
- 网络：云安全组和 Linux 防火墙允许 UDP 9000 入站。
- 自动化测试额外需要 Python 3，并要求 python、g++ 在 PATH 中。

客户端主动发送数据，服务端使用 recvfrom() 得到的来源地址回复。客户端来源端口不需要等于 9000，且可能经过 NAT 映射。

## 编译与运行

### 1. 启动 Linux 服务端

将 server.cpp 上传到服务器，例如在本地项目目录执行：

```powershell
scp .\server.cpp 用户名@服务器公网IP:~/server.cpp
```

在 Linux 上编译并运行：

```bash
cd ~
g++ -std=c++17 -Wall -Wextra -O0 -g server.cpp -o reliable_udp_server
./reliable_udp_server
```

预期输出：

```text
UDP session server listening on 0.0.0.0:9000
Idle timeout: 60s; gap timeout: 30s. Ctrl+C to stop.
```

0.0.0.0 表示绑定本机所有 IPv4 接口，不需要把它替换为公网 IP。更新时先按 Ctrl+C 停止旧程序，再重新编译启动。

### 2. 编译 Windows 客户端

在仓库根目录打开 PowerShell：

```powershell
cd .\Program\reliable-udp
g++ -std=c++17 -Wall -Wextra -O0 -g client.cpp -o reliable_udp_client.exe -lws2_32
```

-lws2_32 用于链接 Windows Winsock 库。Linux 和 Windows 两端必须使用同一版本的会话协议。

### 3. 输入消息

将下面字符串替换为服务器的实际公网 IPv4：

```powershell
$serverIp = "服务器公网IPv4"
.\reliable_udp_client.exe $serverIp
```

客户端先建立会话，随后显示 Message>。输入一行并按回车发送：

```text
[Session opened] <Session ID>
Message> hello
Message 1, attempt 1/3
ACK OK. Message 1
```

收到确认或发生失败之前，客户端不会处理下一条输入。当前采用停等方式，没有多条未确认消息并行发送。

- /quit：发送一次 CLOSE 通知并退出，不能作为普通正文发送。
- 输入结束：同样发送 CLOSE 后退出。
- Ctrl+C：停止进程，不保证发送 CLOSE，由服务端超时清理兜底。
- 连续 60 秒没有符合条件的会话活动：服务端会话过期。客户端没有心跳，下一次发送可能收到 UNKNOWN_SESSION，需要重新启动客户端。
- 重传耗尽或收到当前会话的 ERROR：客户端停止发送后续消息，并尝试通知关闭会话。

## 验证乱序、重复和重传

在 Windows 上运行：

```powershell
.\reliable_udp_client.exe $serverIp --test-order
```

此模式使用新会话，依次发送 Message ID 为 3、1、2、2 的消息，并在每次接纳确认后继续。相同 ID 始终使用相同正文。

预期服务端的 [Deliver] 日志按顺序出现：

```text
ID=1 text=test-1
ID=2 text=test-2
ID=3 text=test-3
```

每条只交付一次；M3 先缓存，M1 到达后只交付 M1，M2 到达后交付 M2 并连续交付 M3。最后重复的 M2 只确认，不再次交付。

服务端默认模拟 ACK 丢失：每第 3 个已接纳 DATA（包括重复 DATA）的回复被跳过。计数是整个服务端共享的，不是每个会话单独计数。HELLO、WELCOME 和 ERROR 不参加该计数。因此，具体哪条请求发生重传，取决于服务端此前接纳过多少个 DATA。

这项模拟只丢回复，不模拟请求丢失、随机延迟或真实网络乱序。--test-order 是主动构造乱序 ID 的功能测试。

## 报文格式

协议使用文本字段。nonce 和 sid 均为 32 个小写十六进制字符；mid 为无符号 32 位整数的十进制表示，业务消息 ID 从 1 开始。下面尖括号表示占位符，不是实际报文内容。

| 方向             | 格式                        | 含义                               |
| ---------------- | --------------------------- | ---------------------------------- |
| 客户端 → 服务端 | `HELLO:<nonce>`           | 建立会话请求                       |
| 服务端 → 客户端 | `WELCOME:<nonce>:<sid>`   | 返回与该请求对应的 Session ID      |
| 服务端 → 客户端 | `BUSY:<nonce>`            | 会话数量达到上限，拒绝创建         |
| 客户端 → 服务端 | `DATA:<sid>:<mid>:<正文>` | 发送或重传业务消息                 |
| 服务端 → 客户端 | `ACK:<sid>:<mid>:`        | 确认已接纳该消息，末尾冒号必须保留 |
| 服务端 → 客户端 | `ERROR:<sid>:<原因>`      | 拒绝或报告会话错误                 |
| 客户端 → 服务端 | `CLOSE:<sid>`             | 尽力关闭通知，没有关闭确认报文     |

正文可以为空，也可以包含冒号。解析器按实际接收长度读取，不依赖空字符结尾，并检查 ID 格式和整数溢出。

ACK 的正文为空，不再原样回显业务正文。它确认的是会话中的消息身份。

### 错误与处理

| 原因            | 服务端行为                                             | 当前客户端行为   |
| --------------- | ------------------------------------------------------ | ---------------- |
| UNKNOWN_SESSION | Session ID 不存在或来源地址不匹配，不创建新状态        | 停止当前会话     |
| BAD_MESSAGE     | 拒绝非法 ID、正文长度或消息格式，不确认                | 停止当前会话     |
| ID_CONFLICT     | 同一未交付 ID 的缓存正文冲突，删除整个会话             | 停止当前会话     |
| RECEIVE_LIMIT   | 拒绝超出接收窗口或缓存容量的新消息，保留此前接纳的缓存 | 停止并尝试 CLOSE |

无法识别的报文或非法外层格式可能直接被丢弃，没有 ERROR 回复。已经交付的旧 ID 只做身份去重，不保留历史正文作永久比较。

## 默认参数

| 参数                 | 值          | 说明                                         |
| -------------------- | ----------- | -------------------------------------------- |
| 服务端端口           | UDP 9000    | 客户端与服务端代码中的固定值                 |
| MAX_ATTEMPTS         | 3           | 首次发送加最多 2 次重传；握手也最多尝试 3 次 |
| REPLY_TIMEOUT        | 5 秒        | 每次发送后的固定等待期限                     |
| MAX_SESSIONS         | 128         | 当前保留的会话总数                           |
| RECEIVE_WINDOW       | 64          | 对未来 ID 要求 mid - next_id ≤ 64           |
| MAX_PENDING_MESSAGES | 64          | 单会话乱序缓存条数                           |
| MAX_PENDING_BYTES    | 256 KiB     | 单会话缓存正文总字节数，不含容器开销         |
| MAX_CONTENT_BYTES    | 65,458 字节 | 65,507 减去 49 字节的最长 DATA 头部          |
| IDLE_TIMEOUT         | 60 秒       | 会话空闲过期                                 |
| GAP_TIMEOUT          | 30 秒       | 有缓存缺口且交付进度未推进时过期             |

65,458 字节是当前代码接受的正文上限，不是推荐的数据报大小，也不是路径 MTU 保证。项目尚未实现应用层分片和重组，实验宜先使用短文本。

## 可靠有序的边界

- 顺序只在单个有效会话内成立，交付依据是 Message ID。
- ACK 表示已经接纳，可能仅进入乱序缓存，不代表业务已经执行成功。
- 会话关闭或失效会清理缓存，因此已经 ACK 的乱序消息也可能未交付。
- 重试失败表示结果未确认，不能推断服务端没有执行；ACK 本身可能丢失。
- 服务端状态只保存在内存中。进程重启后旧会话失效，没有跨重启恢复或业务事务保证。
- 会话绑定创建时的来源 IP 和端口，没有地址迁移；NAT 映射变化可能导致会话被拒绝。
- 没有心跳或主动过期通知；客户端通常在再次发送时才得知会话失效。
- 没有加密、认证或防伪造机制；随机会话标识用于隔离状态，不等于认证。
- 没有服务端主动发送业务消息的可靠通道、动态重传计时、拥塞控制或多通道调度。
- 此版本不是 KCP，也不是完整的 Gaffer Packet ACK 方案，而是学习用的消息级实现。

## 常见现象

| 现象                           | 检查方向                                                         |
| ------------------------------ | ---------------------------------------------------------------- |
| HELLO 一直超时                 | 服务端是否运行、IP 是否正确、UDP 9000 是否放行、两端协议是否一致 |
| ACK OK 之前等待约 5 秒         | 可能正好触发服务端模拟丢 ACK，也可能是真实丢包                   |
| UNKNOWN_SESSION                | 空闲过期、缺口过期、服务端重启、会话已关闭或来源地址改变         |
| RECEIVE_LIMIT                  | 消息 ID 提前太多，或乱序缓存条数/正文总量达到限制                |
| ID_CONFLICT                    | 同一会话内同一未交付 ID 被用于不同正文                           |
| 客户端输入新消息却没有立即处理 | 上一条仍在等待 ACK 或重传，这是停等流程                          |
| 测试程序启动失败               | 本机 UDP 9000 被占用，或 Python / MinGW-w64 g++ 不在 PATH 中     |
